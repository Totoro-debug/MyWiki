# 一、Redis 基础

## (一) Redis 性能高/速度快的原因

- 基于**内存**。
- 高效的**数据结构**，可以在`O(1)`时间内完成数据读写。
- 使用**单线程**事件循环，不存在多线程之间的竞争，也不用进行上下文切换。
- 使用 **I/O 多路复用**模型处理客户端请求，单线程可以同时处理多个连接，提高并发。
- 自定义**通信协议 RESP**，序列化和反序列化性能好。

## (二) 线程模型

- Redis 处理客户端请求、执行命令、发送响应的过程是单线程的。后续增加了一些后台线程，用来异步关闭文件、异步 AOF 刷盘、异步内存释放等。
- 在 Redis 6.0 后，使用多个 IO 线程辅助主线程发送响应数据，如果配置`io-threads 4`就会创建 3 个 io 线程。如果希望 io 线程也可以辅助读请求，需要配置`io-threads-do-reads yes`。

![](https://cdn.nlark.com/yuque/0/2026/png/46298582/1773321730250-b8681b96-ccd6-4719-87bf-95dd0bdfbb70.png)

- I/O 多路复用：Redis 使用一个线程记录追踪多个 Socket 的状态。

- 蓝色部分是一个事件循环，由主线程负责的，可以看到网络 I/O 和命令处理都是单线程。 Redis 初始化的时候，会做下面这几件事情：

- 首先，调用 epoll_create() 创建一个 epoll 对象和调用 socket() 创建一个服务端 socket；
- 然后，调用 bind() 绑定端口和调用 listen() 监听该 socket；
- 然后，将调用 epoll_ctl() 将 listen socket 加入到 epoll，同时注册「连接事件」处理函数。

- 初始化完后，主线程就进入到一个事件循环函数，主要会做以下事情：

- 首先，先调用处理发送队列函数，看是发送队列里是否有任务，如果有发送任务，则通过 write 函数将客户端发送缓存区里的数据发送出去，如果这一轮数据没有发送完，就会注册写事件处理函数，等待 epoll_wait 发现可写后再处理 。
- 接着，调用 epoll_wait 函数等待事件的到来：

- 如果是**连接**事件，则会调用连接事件处理函数：调用 **accpet** 获取已连接的 socket，调用 epoll_ctl 将已连接的 socket 加入到 epoll，最后注册「读事件」处理函数；。
- 如果是**读**事件，则会调用读事件处理函数：调用 **read** 获取客户端发送的数据，解析并处理命令，将客户端对象添加到发送队列，将执行结果写到发送缓存区等待发送。
- 如果是**写**事件，则会调用写事件处理函数：通过 **write** 函数将客户端发送缓存区里的数据发送出去，如果这一轮数据没有发送完，就会继续注册写事件处理函数，等待 epoll_wait 发现可写后再处理 。

## (三) 事务

### 1. 原子性

- Redis 执行单个命令是原子性的，执行多个命令可以通过 Lua 脚本实现原子性。

- Lua 脚本运行时出错并中途结束，出错之后的命令是不会被执行的。并且，出错之前执行的命令是**无法被撤销**的，无法实现类似关系型数据库执行失败可以回滚的那种原子性效果。

### 2. 事务

- Redis 可以用通过在一组命令前后增加`MULTI`、`EXEC`命令开启事务。
- 事务执行期间，如果存在**语法错误**，则整个事务都不会执行；如果存在**运行时错误**，会跳过出错命令继续执行后续命令，并且 Redis **不支持回滚**机制。

|   |   |
|---|---|
|命令|功能描述|
|MULTI|开启事务，后续输入的普通命令会被加入“事务队列”并返回 `QUEUED`|
|EXEC|执行事务队列中的所有命令，返回各命令的执行结果（按入队顺序）|
|DISCARD|放弃事务，清空事务队列，所有入队命令都不执行|
|WATCH|监视一个或多个键，若事务执行前这些键被其他客户端修改，事务会被打断（取消执行）|
|UNWATCH|取消对所有键的监视，通常用于放弃事务后重置监视状态|

## (四) 批量操作

- 原生、pipeline、lua 脚本

### 1. 原生批量操作命令

- MGET/MSET、HMEGT/HMSET
- cluster 模式下，如果多个 key 不在同一个槽上，可能还是需要多次传输

- 找到 key 对应的所有 hash slot；
- 分别向对应的 Redis 节点发起 MGET 请求获取数据；
- 等待所有请求执行结束，重新组装结果数据，保持跟入参 key 的顺序一致，然后返回结果。

### 2. pipeline 操作

- 将一批 Redis 命令封装成一组，这些 Redis 命令会被一次性提交到 Redis 服务器，只需要一次网络传输。但是 pipeline 不是原子操作，且在 cluster 模式下同样存在 **key 映射**问题。

## (五) 缓存

- 内存淘汰、内存过期：一致性差，但是维护成本低。
- 主动更新：一致性高，但是维护成本高。

### 1. 主动更新策略

|   |   |   |
|---|---|---|
|策略|说明|优缺点|
|Cache Aside|由缓存调用者维护数据库和缓存的一致性。更新数据时，直接更新数据库并删除缓存。|① 一致性一般。<br><br>② 实现简单。|
|Read/Write Through|缓存和数据库集成为一个服务，由服务维护缓存。调用者不用关心缓存一致性问题。|① 一致性优秀。<br><br>② 实现复杂，性能差。|
|Write Behind Caching|调用者直接读写缓存，其他线程异步将缓存同步到数据库。|① 一致性差。<br><br>② 实现复杂，但性能好。|

### 2. Cache Aside

1. 为什么更新时**删除缓存**而不是更新缓存？

- 更新缓存：如果短时间内没有查询，但是更新多，会导致很多无效更新。并且存在线程安全问题。
- **删除缓存**：本质是延迟更新，更新时使缓存失效，查询时再更新缓存。没有无效更新，线程安全问题较少。

2. **先更新数据库** vs **先删除缓存**？

- **先删除缓存，再更新数据库**：因为更新数据库耗时较长，更新数据库期间其他线程查询数据库并更新缓存的概率更大，出现不一致的可能性更大。

![](https://cdn.nlark.com/yuque/0/2025/png/46298582/1759580238303-774b3ed7-416b-491b-911b-e6ee5e27c17a.png)

- **先更新数据库，再删除缓存**：因为写缓存更快，出现不一致的可能性较小。

![](https://cdn.nlark.com/yuque/0/2025/png/46298582/1759580267649-46b3b2ce-a698-44d7-bfa4-277b67aad593.png)

### 3. 缓存一致性的最佳实践

- **低一致性**需求：Redis 的内存过期+内存淘汰。
- **高一致性**需求：主动更新(Cache Aside) + 过期删除

- **读**操作：命中直接返回；未命中查数据库，写入缓存并设置过期时间。
- **写**操作：先更新数据库，然后删除缓存。

# 二、数据结构

## (一) redisDb

- Redis 默认有 16 个数据库，每一个数据库就是一个 `redisDb`。
- 哈希表`dict`存储所有的键值对，key 是键的字符串，value 是值的 `redisObject`。
- 哈希表`expires`存储所有带过期时间的键及其到期时间，key 是指向 dict 对应键的指针，value 是键的到期时间戳。

```
typedef struct  {
    dict *dict;                 // 存储当前数据库的所有键值对（键空间）
    dict *expires;              // 存储键的过期时间（key -> 过期时间戳）
    dict *blocking_keys;        // 记录因为BLPOP、BRPOP等阻塞的键及等待的客户端
    dict *ready_keys;           // 记录已就绪的阻塞键，用于唤醒阻塞的客户端
    dict *watched_keys;         // 记录被 WATCH 命令监视的键，用于事务
    int id;                     // 数据库 id，默认 0~15
    long long avg_ttl;          // 所有键的平均 TTL，用于统计
    unsigned long expires_cursor; // 过期键遍历的游标（用于定期删除过期键）
    ……
} redisDb;
```

## (二) RedisObject

- 所有数据类型都会封装为 RedisObject，方便管理。

```
typedef struct redisObject {
    unsigned type:4;		// 表示数据类型
    unsigned encoding:4;    // 编码方式，即对象的底层存储结构
    unsigned lru:LRU_BITS;  // LRU_BITS默认24，记录对象最后一次被访问的时间
    int refcount;   		// 4B，对象引用计数器，计数器归 0 时表示对象可以回收
    void *ptr;              // 8B，数据实际存储的内存地址
} robj;
```

- 编码方式

|   |   |   |
|---|---|---|
|编号|编码方式|说明|
|0|OBJ_ENCODING_RAW|raw 编码的动态字符串|
|1|OBJ_ENCODING_INT|整数字符串|
|2|OBJ_ENCODING_HT|hash 表|
|3|OBJ_ENCODING_ZIPMAP|已废弃|
|4|OBJ_ENCODING_LINKEDLIST|双端链表|
|5|OBJ_ENCODING_ZIPLIST|压缩列表|
|6|OBJ_ENCODING_INTSET|整数集合|
|7|OBJ_ENCODING_SKIPLIST|跳表|
|8|OBJ_ENCODING_EMBSTR|embstr 编码的动态字符串|
|9|OBJ_ENCODING_QUICKLIST|快速列表|
|10|OBJ_ENCODING_STREAM|Stream 流|
|11|OBJ_ENCODING_LISTPACK|紧凑列表|

- 数据结构

|   |   |
|---|---|
|数据结构|编码方式|
|String|int、raw、embstr|
|Hash|Dict、ZipList（7.0 之前）、ListPack（7.0 开始）|
|List|ZipList + LinkedList（3.2 之前）、QuickList（3.2 开始）|
|Set|IntSet、Dict|
|SortedSet|Dict + SkipList、ZipList（7.0 之前）、ListPack（7.0 开始）|

## (三) String

- String 经过编码后以字节数组的形式存储，单个 String 最大不能超过 **512MB**。

- `int`如果字符串为纯数字且不超出 64 位长整型范围，按 64 位长整型存储（8B）。
- `embstr`当字符串字节数<= 44B 时，使用连续空间存储 sdshdr 结构体和字节数组。
- `raw`sdshdr 结构体和字节数组存储在 2 块内存中，分配和释放都需要两次。

- String 底层基于 `Simple Dynamic String, SDS` 实现。

- C 中 char 是一个字节，所以 buf 等价于字节数组。且不会发生溢出，发生修改时如果空间不够会先扩容。
- 因为 **len** 字段的存在，获取字符串长度的复杂度 **O(1)**，且不存在二进制安全问题。

```
struct sdshdr8 {
    uint8_t len;        // 字符串长度（已使用字节数）
    uint8_t alloc;      // 总分配字节数（len ≤ alloc）
    unsigned char flags;// 编码标记（如 SDS_TYPE_8）
    char buf[];         // 字符串数据（柔性数组，存储实际字符）
};
```

- 适合存储**对象**，比 Hash 更适合存储复杂的嵌套对象。

## (四) List

- List 按插入顺序存储元素，操作头尾元素非常快，但是查询元素较慢。
- 命令：LPOP、RPOP、LRANGE
- 3.2 之前

- `ZipList`当元素数量<=512 且元素长度<=64B 时，使用连续内存存储。
- `LinkedList`当超出上述阈值时，会自动转换为带头尾指针的双向链表。

- 3.2 开始

- `QuickList`整体是一个双向链表，每个节点相当于 ZipList。

## (五) Hash

- `ZipList/ListPack` 当键值对数量<=512 且键/值长度<=64B 时，field 和 value 交替作为元素存储在数组中。
- `ListPack` 是一个连续的字节数组，头部信息比 ZipList 更少。

- 解决了**连锁更新**问题：每个元素不再存储前一个元素长度，改为存储自身长度。
- 遍历效率更高。

- `Dict`当超出上述阈值时，使用哈希表存储，链表法解决哈希冲突。

- 哈希表使用**渐进式 rehash** 完成扩容。在 rehash 期间，每次发起 Hash 请求时，就将对应槽的所有键值对迁移到新的哈希表上。当发起的 Hash 请求足够多后，就能完成扩容操作。
- 在扩容过程中，如果有插入操作，直接保存到新的哈希表中。如果有查询操作，先查旧哈希表，如果没查到再查新哈希表。

### 1. 应用

1. Redisson 的分布式锁 RedissonLock 使用 Hash 实现，key 就是自定义的锁名称，field 是 `UUID: threadId`，value 是该线程的重入次数。
2. 适合存储字段比较多、且经常修改某些字段的对象。

## (六) Set

- Set 是一个无序集合，查找速度快，支持并集、交集、差集。
- `IntSet`当所有元素都是整数并且元素数量<=512 时，通过有序数组存储，插入时二分查找定位 + 编码升级 + 元素后移。
- `Dict`当不满足上述条件时，使用哈希表存储。

## (七) SortedSet/ZSet

- SortedSet 是一个有序集合，节点按 score 升序排序，分数相同时按元素字典排序。
- `ZipList/ ListPack`当元素个数<=128 且元素长度<=64B 时，按分数排序，连续内存。
- `SkipList + Dict`当上述条件不满足时，使用跳表+哈希表存储：① SkipList 负责按 score 有序存储和遍历；② 哈希表 (key 为元素、value 为 score) 负责查询指定元素的 score。

### 1. SkipList

```
typedef struct zskiplist {
    struct zskiplistNode *header, *tail; // 头尾指针
    unsigned long length;                // 节点个数
    int level;                           // 跳表最大层级，默认32
} zskiplist;

typedef struct zskiplistNode {
    sds ele;                	// 元素值
    double score;           	// 元素分数
    struct zskiplistNode *backward; 	// 前驱节点（用于反向遍历）
    struct zskiplistLevel {
        struct zskiplistNode *forward;	// 后继节点
        unsigned long span;				// 跨度
    } level[];							// 层级指针数组
} zskiplistNode;
```

- SkipList 是一个**多层有序链表**，负责按 score 有序存储和遍历。
- 每个节点包含多个层级指针，每个层级的指针指向下一个拥有该层级的节点、跨度表示两个节点之间的距离，层级越高的指针跳过的节点越多。
- SkipList 头节点层级数组的长度就等于最大层数，从头节点开始可以实现类似二分查找的效果，查找效率接近`O(logN)`。
- 节点层高设置

- 创建节点时生成 `[0,1]`之间的随机数，随机数<0.25 则层数增加一层，直到随机数大于 0.25 或者达到最大层数限制。

### 2. 为什么不用 B+树

1. SkipList 实现更加简单，不用进行节点的分裂和合并，但是需要维护节点各层级指针的关系。
2. SkipList 写入性能更高，单点查询性能不低于 B+树，范围查询性能比 B+树稍低。

## (八) GEO

- 使用 **GeoHash** 算法将经纬度转换为一个整数，将其作为 score 存储到 ZSet 中，然后利用 ZSet 的有序性来实现范围查询和距离计算。

```
GEORADIUS key longitude latitude radius  	# 根据经纬度查找元素
GEORADIUSBYMEMBER key member radius				# 根据成员查找元素
```

## (九) BitMap

- 使用 String 实现，上限 512MB 即可以存储 2^32 个 bit。
- 可以用于签到、点赞、用户统计。

```
BITCOUNT key start end	// 获取 start 和 end 之间值为 1 的元素个数
```

## (十) HyperLogLog

- 从 Loglog 算法派生的概率算法，用来估计超大集合的中不重复元素的数量，且不需要存储所有元素。
- 基于 String 实现，单个 HLL 占用内存小于 16KB，但是结果有 0.81%的误差。

```
PFCOUNT key1 key2	// 获取一个或者多个 HyperLogLog 的唯一计数。
PFMERGE destkey sourcekey1 sourcekey2 ...
// 将多个 HyperLogLog 合并到 destkey 中，destkey 会结合多个源，算出对应的唯一计数。
```

# 三、内存回收

## (一) 内存过期策略

- Redis 删除过期 Key 采用延迟删除的策略，具体使用**惰性删除** + **定期删除**两种策略。

### 1. 惰性删除

- Redis 不主动删除 Key，只在每次**访问 Key** 时调用 `**expireIfNeeded**(redisDb *db, robj *key,)` 检查 Key 是否过期，如果设置了过期时间且已经过期则通过异步/同步方式删除该 Key；否则，返回实际数据。

### 2. 定期删除

- Redis **周期**性地从 `expires`中抽取一定数量 key 进行检查，并删除其中过期的 Key。

- 频率由 `server.hz` 控制，默认为 10 即每秒钟 10 次，每周期 100ms。
- 每次扫描最多执行 25% 个周期即 25ms，如果本次抽取过期 Key 占比超过 25%=5 个，并且暂时没有超时就再抽取一次；如果超时则立即结束该周期。
- 每次抽取 key 数量由`ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP`控制，值为 20。

## (二) 内存淘汰策略

- 在 32 位系统，redis 默认最大容量是 3GB；在 64 位系统，默认是 0 表示无限制。
- redis 在运行时，可以通过命令**动态扩容**。
- Redis 每次执行命令前，都会判断内存是否达到上限`server.maxmemory`，如果达到上限会执行 `performEvictions()`⽅法尝试淘汰 Key 释放内存，如果内存仍然不足则拒绝执行写入命令。
- 执行流程

- 初始化固定大小（默认 16）的候选池。
- 首先随机抽取`maxmemory-samples`个键，全部放入候选池。后续抽取，如果键比候选池中淘汰优先级最低的键要高，则替换。
- 最后从候选池中选择淘汰优先级最高的键淘汰。

- 当使用`LRU`时，redisObject 的 lru 字段记录最后一次访问时间；当使用`LFU`时，高 16 位记录最后一次访问时间，低 8 位记录逻辑访问次数。

|   |   |
|---|---|
|淘汰策略|说明|
|**noeviction**|默认策略。不淘汰 Key，内存满时拒绝执行写入操作。|
|**allkeys-lru**|淘汰所有键中最近最少使用的键|
|**allkeys-lfu**|淘汰所有键中使用频率最低的键|
|**allkeys-random**|随机淘汰所有键|
|**volatile-lru**|淘汰过期键中最近最少使用的键|
|**volatile-lfu**|淘汰过期键中使用频率最低的键|
|**volatile-ttl**|淘汰过期键中剩余生存时间（TTL）最短的键|
|**volatile-random**|随机淘汰过期键|

# 四、Redis 持久化

## (一) RDB（Redis Database Backup file）

- RDB 保存的是某一时刻的 Redis **内存快照**。Redis 重启后读取 RDB 文件可以快速恢复数据。

- 缺点

- RDB 执行间隔时间长，两次RDB之间写入的数据有丢失风险。
- **fork** 子进程、压缩、写出 RDB 文件都比较耗时。

1. **RDB 自动执行**

- Redis **服务停止**时，自动进行 RDB。
- `redis.conf`中配置`save seconds count`，Redis 在执行周期任务时会检查是否满足在 seconds 秒内发生 count 次 Key 的修改操作，如果满足就通过`**bgsave**`进行 RDB。

2. **RDB 手动执行**

- `save` 由主线程写入 RDB 文件，期间会**阻塞**所有客户端请求。
- `bgsave`通过 `fork()` 得到子进程，fork 操作本身会阻塞主进程，子进程复制得到父进程的页表，然后由子进程完成持久化。子进程采用写时复制（**copy-on-write**），主进程修改数据时，复制被修改的数据页，子进程读取副本，主进程操作原页面，保证 RDB 记录的是 fork 发生时的快照。

## (二) AOF（Append Only File）

- AOF 默认关闭，需要在`redis.conf`中配置开启。
- Redis 执行的每一个写命令都会记录在 AOF 文件，相当于**写命令执行日志**。每次先执行写命令，然后将命令写入 **AOF 缓冲区**，由**后台线程** aof_fsync 根据配置调用系统调用将缓冲区写回硬盘。

- 先执行命令后写 AOF，可以避免额外的**检查开销**、且**不会阻塞命令**执行。

- `**bgrewriteaof**`命令可以重写 AOF 文件，用更少的命令达到相同的效果，减少 AOF 文件大小和同一个 Key 多次写的问题。

- 当调用`bgrewriteaof`、AOF 过大、AOF 增大 1 倍时，fork 一个子进程，子进程会读取当前数据库生成一个新的 AOF 文件。在此期间，主进程维护一个 AOF 重写缓冲区记录此期间所有新的写命令，重写完成后追加到新 AOF 文件末尾。最后新 AOF 文件替换旧 AOF 文件。

- AOF 写回频率

|   |   |   |   |
|---|---|---|---|
||说明|优点|缺点|
|always|每次执行写命令，放入 AOF 缓冲区，然后立即将缓冲区写回硬盘。|可靠性高，几乎不丢数据|性能差|
|everysec|每次执行完写命令，放入 AOF 缓冲区。后台线程 aof_fsync 每隔 1 秒将缓冲区数据写回硬盘。|性能适中|可能丢失1秒数据|
|no|每次执行完写命令，放入 AOF 缓冲区，有操作系统控制写回时机。|性能最好|可靠性较差，可能丢失大量数据|

## (三) 混合持久化

- AOF 重写时，子进程将内存快照按照 RDB 方式写入 AOF 文件，主进程依旧将此期间所有写命令写入 AOF 重写缓冲区。重写完成后，将缓冲区内容追加到新 AOF 文件中。
- redis7.0 后默认开启。Redis 重启更快，降低大量数据丢失的风险。

# 五、Redis 集群

## (一) 主从集群

### 1. 主从集群的结构

- 主从集群中有一个 `master` 节点、若干个 `slave/replica` 节点。当客户端访问 Redis 服务器时，读操作可以访问从节点，写操作访问主节点，主节点自动将数据同步给从节点。
- 在从节点的配置文件中设置`slaveof masterip masterport`，或让从节点执行该命令。
- 如果主节点 key 过期了，该 key 被访问或被淘汰，主节点会发送 **del** 给从节点。

### 2. 主从同步

- `**replication buffer**` 记录主节点生成 RDB、发送 RDB、从节点加载 RBD 期间所有的写命令
- `**Replication id/replid**` 该节点数据集的标志，replid 一致就表示数据集一致。每个主节点都有**唯一**的 replid，从节点会继承主节点的 replid。
- `**repl_baklog**` 当主从节点完成第一次连接后，repl_baklog 文件会记录所有的**写命令**。
- `**offset**`：表示 repl_baklog 中的数据长度。repl_baklog 中记录的写命令越多，offset 越大。从节点完成同步后记录当前 offset，主从 offset 一致表示数据一致，从 offset 小于主 offset 表示数据落后，需要进行同步。

1. **全量同步**

- 从节点执行 **replicaof** 命令后会发送 `**psync** replid offset`请求同步，主节点发现 replid 不一致，向从节点返回 `**fullresync** replid offset`。
- 主节点执行`**bgsave**`fork 子进程生成 **RDB** 文件，然后将 RDB 文件发送给从节点，从节点清空本地数据并加载 RDB 文件。在上述期间，主节点都要所有写命令写入 **replication buffer**。
- 主节点收到从节点 RDB 加载完成的**确认消息**后，发送 replication buffer 中的写命令，从节点执行接收到的命令。

2. **增量同步**

- 从节点重启后，自动重连并发送`psync replid offset`请求，主节点判断 replid 一致且增量数据保留，向从节点返回 continue。
- 主节点从 **repl_baklog** 文件中获取从节点 offset 后的命令，写入 replication buffer 中，replication buffer 会将写命令发送给从节点。
- 在正常运行的过程中，主节点会将写命令发送给从节点，并且将写命令写入 repl_baklog。

3. **repl_baklog**

- repl_baklog 默认大小为 1M，文件写满后覆盖最早的数据，逻辑上相当于大小固定的循环数组。
- 如果从节点断开时间过长或者网络阻塞等，可能导致从节点未同步的增量数据被覆盖，此时只能再次进行全量同步。

### 3. 脑裂数据丢失问题

- 如果主节点和从节点之间出现通信问题，但是客户端可以和主节点通信，客户端一直向主节点写入数据。此时哨兵会在从节点中选举出一个新的主节点，主节点在恢复网络通信或者重启后，会被降级为从节点并且清空数据，导致之前过程中客户端写入的数据丢失。
- 解决方法：当主节点发现**从节点数量小于一定数量**或者**主从通信超过一定延迟**，就**拒绝客户端的写操作**。

- `min-slaves-to-write x`主节点必须要有至少 x 个从节点连接，如果小于这个数，主节点会禁止写数据。
- `min-slaves-max-lag x`主从数据复制和同步的延迟不能超过 x 秒，如果超过，主节点会禁止写数据。

## (二) 哨兵集群

- **状态监控**：哨兵会不断检查主、从节点是否按预期工作。
- **故障恢复**：如果有主节点故障，哨兵会将一个从节点提升为新的主节点，旧的主节点故障恢复后会向其发送 slaveof 命令设置为新主节点的从节点。
- **状态通知**：哨兵充当 redis 客户端的服务发现来源，当集群发生故障转移时，会将最新集群消息推送给 redis 客户端。

### 1. 状态监控

- 哨兵基于心跳机制检测服务状态，每隔 1 秒向集群的所有节点发送 ping 命令：

1. **主观下线**

- 如果某个哨兵发现某个节点没有在规定时间内响应，则认为该节点主观下线。

2. **客观下线**

- 如果超过指定数量的哨兵都认为该实例主观下线，则该实例客观下线。`quorum`一般超过哨兵数量的一半，哨兵数量至少为 3。

### 2. 选举新的主节点

- 首先判断从节点与主节点断开时间的长短，如果超过指定值，则会排除该从节点。
- 然后判断从节点的 `slave-priority`，越小优先级越高，如果是 0 则不参与选举，默认情况下都是 1。如果`slave-priority`相同，则 offset 越大的数据越新，优先级越高。
- 最后判断从节点的 `run_id` 大小，越小优先级越高。run_id 是创建节点时随机生成的。

### 3. 故障转移

- 首先哨兵投票选出一个 leader 哨兵，第一个确定主节点客观下线的人会立刻发起投票。票数超过哨兵数一半且超过 querum 的哨兵成为 leader，一般第一个发起投票的会成为 leader。
- leader 哨兵向上面选中的从节点发送`slaveof no one`命令，让该节点成为主节点。
- leader 哨兵向其余从节点发送`slaveof masterip masterport`命令，并开始数据同步。
- 当故障节点恢复后，哨兵同样会发送命令，使其成为从节点。

## (三) 分片集群

- 使用分片集群可以解决**海量数据存储、高并发写**的问题。
- 集群中有多个主节点，每个主节点保存不同数据。
- 每个主节点都有多个从节点。
- 主节点之间通过 ping 检测互相的健康状态，类似哨兵机制。
- 客户端请求可以访问集群任意节点，最终都会被转发到正确节点。

### 1. 创建集群

```
redis-cli --cluster create --cluster-replicas 1 192.168.240.128:7001 192.168.240.128:7002 192.168.240.128:7003 192.168.240.128:8001 192.168.240.128:8002 192.168.240.128:8003
```

- `--cluster` 表示集群操作。
- `create` 创建集群。
- `--cluster-replicas 1` 指定集群中每个主节点的从节点的个数。

### 2. 散列插槽

- Redis 分片集群共有 **16384** 个哈希槽即 0~16383。在创建集群时，Redis 会将插槽分别映射到所有主节点上。
- 数据的 key 会被映射到一个插槽中，访问 Key 时会根据 Key 的有效部分用 CRC16 算法得到哈希值。然后用 16384 对哈希值取模，结果就是哈希槽编号。最后根据哈希槽和节点的映射关系，访问对应节点。
- Key 的有效部分，分为两种情况

- key 中不包含 "{}"，则整个 key 都是有效部分。
- key 中包含 "{}"，并且里面至少包含一个字符，则 "{}" 中字符是有效部分。

### 3. 故障转移

- 当集群中主节点宕机时，该实例就会与其它实例断开连接，然后就会疑似宕机，最后确定下线，自动提升一个从节点为新的主节点。
- 使用`cluster failover`命令可以手动让集群中的主节点宕机，切换到执行 cluster failover 的从节点，实现无感知的数据迁移。

- 从节点会让主节点拒绝客户端的所有要求，然后主节点返回当前的数据 offset。
- 当从节点的 offset 与主节点一致时，开始故障转移。
- 从节点标记自己为主节点，然后广播故障转移的结果。

# 六、常见问题

## (一) BigKey 问题

- 一个 key 对应的 value 所占用的内存比较大，那这个 key 就可以看作是 bigkey。
- 影响：响应超时、网络阻塞、工作线程阻塞。

### 1. 检查

- `**redis-cli -p 6379 --bigkeys**` 对所有 key 进行扫描，对 redis 性能有影响，并且只会给出每种数据结构中最大的 key。
- `**SCAN**` 命令可以按照一定的模式和数量返回匹配的 key。获取了 key 之后，可以利用 STRLEN、HLEN、LLEN 等命令返回其长度或成员数量。

### 2. 处理

- 分割大 key。
- 开启 **lazy-free**：懒惰删除是 Redis 4.0 开始引入的，指的是让 Redis 采用**异步**方式延迟释放 key 使用的内存，将该操作交给后台线程处理，避免阻塞主线程。例如：unlink key。

## (二) 热点 Key

- 某个 Key 一段时间被大量访问（高并发）。

1. **本地缓存**

- 将 hotkey 存储到本地缓存。

2. **读写分离**

- 主从复制，让从节点分担读压力。

3. **拆分热 Key**

- 通过 **{}** 机制，将热 key 映射到不同节点。

## (三) 缓存穿透

- 缓存穿透指用户查询的数据在**缓存和数据库中都不存在**，缓存永远不生效，请求会直达数据库。如果一直发起这类请求，就会导致数据库负载过重。

1. **缓存空对象**

- 对于数据库中不存在的对象，缓存一个空对象，并设置较短存活时间。
- 优点：实现简单，维护方便。
- 缺点：额外的内存消耗（设置TTL），可能造成短期的数据不一致。

2. **布隆过滤器**

- bit 数组 + 一组哈希函数，适用于海量数据的存在性检测。
- 存在的数据一定判定为存在，不存在的数据可能误判为存在。
- 优点：内存占用少，不用缓存多余的 key 和空对象，判断非常高效。
- 缺点：实现复杂，存在误判的可能。

## (四) 缓存雪崩

- 缓存雪崩指**大量的缓存 Key 同时/极短时间内失效**或者 **Redis 服务宕机**，导致大量的请求同时到达数据库，导致数据库压力过大。
- 解决方法

- 缓存预热时不同的 Key 的 TTL 额外增加**随机值**。
- 使用 **Redis 集群**提高服务的可用性。
- 使用限流策略、熔断机制等保证缓存可用性。
- 使用多级缓存减少 Redis 和数据库的压力。

## (五) 缓存击穿/热点 Key 过期

- 缓存击穿指一个被**高并发访问**并且**缓存重建业务较复杂**的 key 突然失效了，大量的请求会在瞬间给数据库带来巨大的冲击。
- 在使用 LFU 策略的前提下，可以使用 `redis-cli -p 6379 --hotkeys`查找热点 key。

1. **互斥锁**

- 为重建缓存的过程加锁，同时只有**一个线程**可以访问数据库并重建缓存。配合双重检验锁，其他线程在该线程重建完缓存后就可以读取缓存。
- 优点：实现简单，没有额外的内存消耗，可以保证一致性。
- 缺点：线程需要等待，性能受影响，可能有死锁风险。

2. **逻辑过期**

- 缓存不设置有效期，而是将过期时间作为数据一部分存入缓存。查询缓存时如果发现缓存逻辑上过期，启动另一个线程异步重建缓存，当前线程以及重建过程中的其他线程直接返回旧数据。
- 优点：线程无需等待，性能较好。
- 缺点：不能保证一致性；有额外内存消耗。

# 七、Redis 充当消息中间件

## (一) Pub/Sub（发布订阅）

- 基于“频道-客户端”的映射表。当客户端 SUBSCRIBE channel 时，Redis 会将客户端对象加入该频道的订阅链表。PUBLISH 时，遍历链表将消息推送给所有在线订阅者。
- 适用于实时通知、配置更新、聊天等对可靠性要求不高的场景。
- 特点：消息发完就丢，没有消息持久化能力。

## (二) Stream

- Stream 底层使用 Radix Tree（基数树）存储消息。
- 每个 Stream 有一个唯一的名称也就是设置的 Key，使用 **XADD** 命令添加消息时会自动创建不存在的 Stream。
- **消息链表**：所有消息被串成一个链表，每个消息包含一个唯一的 ID 以及消息内容。
- **消费者组**：使用 `XGROUP CREATE`创建，一个组有多个消费者。每个消费者组有一个游标记录了整个组中发出的最新的消息 ID，也就是说任何一个消费者读取消息都会导致游标移动。
- **pending_ids**：记录当前消费者已经读取但是还没有应答 XACK 的消息 ID 集合。未确认消息支持重试和死信处理。
