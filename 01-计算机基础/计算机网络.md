# 一、输入网址发生了什么

- 浏览器进行 URL 解析，得到协议版本、域名、端口等信息。
- 解析域名，首先查询是否存在相应 DNS 缓存，例如：浏览器、系统缓存、路由器缓存等，不存在缓存就查询 DNS 服务器。(本地 -> 根 -> 顶级 -> 权威)
- 封装为 http 报文，和目标服务器建立 Http 连接。
- 首先，建立 tcp 连接，三次握手。
- 如果是 HTTPS，还要进行 TLS 握手

# 二、网络层

- 网络层主要实现主机间通信，点对点通信。

## (一) IP 基础

### 1. IP 地址

- 32 位正整数，分为**网络号+主机号**两部分，采用**点分十进制**的表示方式。
- 某个网络下最大主机数量 = 2^host位 - 2。

- 主机号全 0 表示本网络地址。
- 主机号全 1 表示在该网络中广播。如果广播地址和主机是同一个网络则是本地广播；反之是直接广播，直接广播不安全会被路由器拦截。

### 2. 无分类地址 CIDR

- 直接将 32 位 IP 地址划分为网络号 + 主机号，通过网络号长度或**子网掩码**确定网络号。

### 3. 子网划分

- 通过**子网掩码**将主机号划分为**子网地址**和**子网主机地址**。

### 4. IP 分片与重组

- 数据链路层最大传输单元 MTU，如果 IP 数据包大小大于 MTU 时，IP 数据包就会被分片，最后由目的主机进行重组。
- 如果一个 IP 数据包的某个分片丢失，就会导致整个 IP 数据包重传。

## (二) IP 路由

- 路由表中记录**目的 IP 地址**与**下一跳 IP** 的地址。如果路由表中存在多条相同网络地址的记录，采用**最长匹配**原则。

## (三) DNS 解析

- 客户端首先向本地 DNS 服务器发送 DNS 请求。
- 本地 DNS 服务器查询本地缓存，如果没有记录，则向根域名服务器发送 DNS 请求。
- 根域名服务器根据顶级域名，将顶级域名服务器 IP 返回给本地域名服务器。
- 本地域名服务器向顶级域名服务器发送请求，顶级域名服务器再将权威域名服务器 ip 返回给本地域名服务器。
- 本地域名服务器向权威域名服务器发送请求，权威域名服务器将查询结果返回给本地域名服务器。
- 本地域名服务器将结果保存到缓存，返回给客户端。

## (四) ARP 协议 — 通过 IP 获取 MAC 地址

- ARP 协议用于将同一个局域网内的 IP 地址转换为 MAC 地址。核心是通过在本地局域网广播 ARP 请求报文，目标主机向源主机返回响应请求，其中携带自己的 MAC 地址。
- RARP 协议用来向指定的 RARP 服务器请求自己的 IP 地址。现在不常用。

## (五) NAT

- 将子网中的私有 IP 地址转换为公有 IP 地址。
- 网络地址与端口转换 NAPT

- 将 IP 地址与端口一起转换，就可以节省公网 IP 地址。
- 一般将子网中不同 IP 地址+端口，转换为同一个公网 IP+不同端口。

## (六) PING 的原理

- ping 基于 ICMP 协议工作。主机构建一个 ICMP Echo Request 报文，然后发到目的主机，目的主机收到报文后返回一个 Echo Reply 报文。
- **如果 ping 不通，但是 http 请求成功，是什么原因？**

- ping 是基于 ICMP 的，而 http 基于 tcp 或 udp，可能是防火墙禁用了 ICMP 协议。

# 三、TCP

① 面向连接

② 可靠

③ 基于字节流。
<img src="00-resource/images/TCP.webp" style="zoom:60%;">

1. **序列号**：每次发起连接时**随机初始化**一个序列号，防止**历史连接**和保证**安全性**。通信中，每发送一次数据，seq 就要累加一次数据字节数。用来解决数据包**乱序**问题。

- 初始序列号：每 4 微秒加一的计时器 + 伪随机函数（MD5、SHA 等）

2. **确认应答号**：下一次期望收到的序列号。发送端收到某个 ACK 报文之后，就认为该 ack 之前的数据对方都正常接受。用来解决**丢包**问题。
3. 控制位

- ACK：除了建立连接的第一个 SYN 包之外，其他 TCP 包该位都应该是 1。
- SYN：用来请求建立连接。
- RST：表示当前报文中四元组唯一确定的这个 TCP 连接有异常，强制重置。
- FIN：发送 FIN 报文的主机不在有数据发送，但是可以接受数据，并期望断开连接。

## (一) 什么是 TCP 连接？怎么确定一个 TCP 连接？

- TCP 连接包括：IP地址与端口（网络四元组）、序列号、窗口大小等。
- 通过四元组：源 IP、目的 IP、源端口、目的端口。

## (二) 三次握手

<img src="00-resource/images/TCP三次握手.png" style="zoom:75%;">

- 客户端在发送出去第三个报文后就处于 `ESTABLISHED` 状态，而服务端在收到第三个报文后处于 ESTABLISHED 状态。第三个报文可以携带应用层数据，前两个不可以。

### 1. TCP 半连接队列和全连接队列

- 服务器调用 listen 后，该套接字就进入**永久监听**状态，直到程序关闭或调用 close。然后内核会为 Socket 维护两个队列，程序调用 accept() 就可以从 Accept 队列取出全连接对象。

- **半连接队列**（SYN 队列）：服务器收到第一个 SYN 报文，创建一个半连接对象并放进队列。
- **全连接队列**（Accept 队列）：服务器收到第三个报文，取出半连接对象并创建全连接对象放进 Accept 队列。

- 当全连接队列满时，默认会给程序留缓冲时间，即客户端会重试或超时；也可以设置为直接返回 RST 报文，快速失败。

### 2. 什么是 SYN 攻击？怎么防御？

- SYN 攻击就是通过**伪造不同源 IP 或源端口**的 SYN 报文，将服务器的半连接队列占满，服务器无法建立正常连接。

1. 扩展 SYN 队列。
2. 回收连接：缩短超时时间、回收早期连接。
3. 启用 **tcp_syncookies**：当半连接队列满时，不再丢弃 SYN 请求，而是返回一个加密哈希生成的 SYN+ACK 序列号，只有收到合法的 ACK 才分配内存和 socket。

### 3. 为什么三次握手，不是两次握手？

- 至少三次才能确认双方的**接受、发送能力**都正常。
- **防止历史连接**请求成功建立连接。（最重要的原因）
- 避免资源浪费。

- 如果两次握手，服务器不确定客户端有没有收到 SYN+ACK 报文，因此每次收到 SYN 报文都只能先建立连接。因为网络阻塞等原因，客户端超时重传 SYN 报文，那么对于同一条连接会重复分配资源造成浪费。

### 4. 三次握手报文丢失时，客户端和服务器该怎么办？

|   |   |
|---|---|
|第一次|客户端认为服务器没收到 SYN 报文，超时重传 SYN 报文。|
|第二次|客户端认为服务器没收到 SYN 报文，超时重传 SYN 报文。<br><br>服务器认为客户端没收到 SYN + ACK 报文，超时重传 SYN + ACK 报文。|
|第三次|服务器认为客户端没收到 SYN + ACK 报文，超时重传 SYN + ACK 报文。|

## (三) 四次挥手

<img src="00-resource/images/TCP四次挥手.png" style="zoom:75%;">

- 如果四次挥手时，主动方调用的是 **close()** 函数暴力关闭连接，那么在收到被动方的 ACK 报文后，进入 FIN_WAIT_2 状态后不会**无限等待**，而是等待一定时间。
- 如果在等待时间内**没有收到 FIN** 报文，就会**直接断开**连接；如果收到了**数据**，就会返回 **RST** 重置连接。

### 1. 为什么四次挥手？

- 主动方发送 FIN 报文默认调用 **shutdown**() 函数，表示不再发送数据、保留接受能力。
- 被动方首先需要对客户端的 FIN 报文进行应答，被动方可能还有数据要发送，所以先发送 ACK，等到不发送数据时再发送 FIN 请求。

### 2. 可以三次挥手吗？

- 在开启 TCP **延迟确认**机制的前提下，如果被动关闭方也没有数据想要发送，可以选择合并第二次和第三次挥手。

### 3. 四次挥手报文丢失时，客户端和服务该怎么办？

|   |   |
|---|---|
|第一次|客户端认为服务器没收到 FIN 报文，超时重传 FIN 报文。|
|第二次|客户端认为服务器没收到 FIN 报文，超时重传 FIN 报文。|
|第三次|服务器发送完 FIN 报文后进入 **LAST_ACK** 状态，如果 FIN 报文丢失，服务器就收不到客户端的 ACK 报文，服务器会超时重传 FIN 报文。|
|第四次|服务器认为客户端没收到 FIN 报文，超时重传 FIN 报文。客户端重发一次 ACK，重置 TIME_WAITED 的等待时间。|

### 4. 为什么 TIME_WAIT 要等待 2MSL 的时间？

- MSL (Maximum Segment Lifetime，**最大报文生存时间**) 是报文在网络上存在的最大时间，TCP 的 MSL 要**大于 IP 层的 TTL 字段消耗为 0 的时间**（Linux 设置的 MSL 为 30s）。
- 客户端回送 ACK 报文后进入 **TIME_WAITED** 状态，该状态会持续 2MSL 时间后才彻底关闭。如果 ACK 报文丢失，服务器会超时重传 FIN 报文。ACK 丢失 + 重传 FIN 到达客户端加起来就是 2MSL，也就是说**至少允许报文丢失一次**，防止服务器因为没收到 ack 一直重发 FIN 报文。客户端每次收到 FIN 报文就会回送 ACK 报文，并重置 2MSL 的时间。
- 另一方面，等待 2MSL 可以让这个即将关闭的旧连接中的所有数据都失效，减小新连接过程中收到旧连接的几率。

## (四) 可靠传输

### 1. 序号机制

- 序列号 seq、确认号 ack。

### 2. 确认机制

1. **累积确认**

- 发送方连续发送多个报文，只要收到某个 ACK 报文，则认为在此之前的所有报文都成功送达了。

2. **捎带确认**

- 某一方有数据要发送时，可以捎带确认信息，而不是单纯发送 ACK。

3. **延迟确认**

- 如果只发送确认信息，对网络利用率就很低，可以等待一段时间，当有数据时，接受方再发送应答。
- 延迟确认的延迟时间一般不超过超时重传事件 RTO，所以不会导致发送方计时器超时。

### 3. 重传机制

1. **超时重传**

- 发送方发送报文后启动一个**定时器**，如果超时后还没有收到接收方的 ACK 确认，就会重传报文。
- **超时重传时间 RTO** 应该**略大于**报文的**往返时延 RTT**，一般 RTO 是一个动态变化的值。
- 超时重发的报文再次超时重发，超时间隔每次 *2。

2. **快速重传**

- 发送方连续收到**三个相同的 ACK**，就知道接收方没有收到该报文，会立即重传该报文。

3. **选择性确认 SACK**

- TCP 头部的选项字段增加 SACK，记录已收到的数据范围。
- 发送方在收到接收方的三个相同的带 SACK 的 ACK 报文后，检查 **SACK 字段**，然后**重传丢失的部分**。

4. **Duplicate SACK**

- 如果接收方发送的 ACK 报文丢失，触发超时重传；或者发送方的早期报文因为网络问题延迟到达，触发快速重传。最后接收方一定要收到了重复的数据。
- 接收方就会返回 D-SACK 报文，其中 SACK 字段记录重复接收的报文区间，告知发送方不要重复发送。

### 4. 差错控制

- 校验和：报头前面增加一个伪报头（源/目的 IP、协议字段、报头长度）。

## (五) 流量控制

- 控制发送方的发送速率，使得接收方有足够的时间接受并处理收到的数据。
- TCP 使用**滑动窗口协议**进行流量控制，TCP 报头有窗口大小字段可以控制发送窗口的大小。

1. **接收窗口**

- 接收方维护的当前可以接受数据的缓存区大小。发送窗口大小不能大于接口窗口。
- TCP 的报头有一个**窗口大小**字段，接收方可以用来告知发送方接收窗口的大小。

2. **窗口关闭** / 零窗口通知

- 如果发送方发送的过快或者接收方处理数据较慢，接收窗口可能会减少为 0。

- 发送方在收到接收方的**零窗口通知**后，就会启动及一个**持续计时器**，如果计时器超时就发送一个零窗口探测报文。

## (六) 拥塞控制

- 防止发送过多数据到网络中，导致节点或链路过载。**发送方**维护一个拥塞窗口，根据网络拥塞程度动态变化。只要发生**超时重传**，就认为网络出现了阻塞。
- **发送窗口=min[ 接收窗口，拥塞窗口 ]**

### 1. 慢启动

- 拥塞窗口初始大小较小，每收到 1 个 ACK，cwnd 增加 1 字节。因此，每一轮下来 cwnd 都会**翻倍**。

### 2. 拥塞避免

- 当拥塞窗口达到慢启动门限，拥塞窗口增加速率改为**线性增加**。每收到一个 ACK，拥塞窗口增大 1/cwnd 个字节。

### 3. 超时重传

- 如果发送方在计时器超时前，一直没有收到 ACK，就认为发生了拥塞。
- 设置**慢启动门限 = 拥塞窗口 / 2**，然后拥塞窗口重置为初始值重新增加。

### 4. 快速重传

- 如果发送方收到连续三个 ACK，就会立即重传该报文。

### 5. 快速恢复

- 当发生快速重传时，设置**慢启动门限 = 拥塞窗口 / 2**，设置拥塞窗口 = 一半 + 3，其中+3 对应 3 个 ACK 即对方在此之前收到了 3 个报文，然后执行线性增加。

## (七) TCP 粘包和拆包

### 1. 字节流传输

- TCP是面向**字节流**的，虽然应用程序和 TCP 交互是一次一个数据块，但是 TCP 将应用程序给的数据视作无结构的字节流。
- TCP 报文长度由接收窗口、拥塞窗口决定，**发送方**可能会将多个小的数据包合并在一起发送，而**接收方**则可能将这些数据包拆分成多个小的数据包进行接收，从而导致无法区分应用消息的边界。

### 2. 解决方法

1. 发送方和接收方约定**固定的消息长度**。实现简单，但是灵活性差。
2. 消息末尾添加**特殊字符**作为边界，例如：http 的换行符。
3. 自定义消息结构：消息头部中包含**报文长度**。

## (八) 建立连接中、已建立连接的 TCP，收到 SYN 报文怎么办？

- 如果服务器没有维护该 SYN 报文中的四元组唯一确定的连接，服务器会建立新的连接。
- 如果服务器正在维护该 SYN 报文中的四元组唯一确定的连接，服务器会发送自己当前维护的 seq 和 ack 的 ACK 报文。客户端则发送 **RST** 释放历史连接。

## (九) IP 层会分片，为什么 TCP 还要 MSS？

1. MSS 最大报文段长度 = MTU - IP 头部 - TCP 头部

- MSS 表示除去 IP、TCP 头部后，TCP 报文能容纳的最大数据长度。

2. 如果把超过 MTU 的数据交给 IP 层分片，且如果其中一个分片丢失就会导致整个 IP 数据包即整个 TCP 报文都要重传。而由 TCP 进行分片，在丢失某个分片后只需要重传该分片。

## (十) TCP 保活机制（Keepalive）

- TCP 的保活机制是在**内核**中完成的。
- 如果 TCP 连接一直没有数据交互，直到超过了**保活时间**（默认 7200 秒）。服务器就会开始每隔一段时间（默认 75 秒）向客户端发送一个探测报文。

- 如果客户端是正常工作的就会返回响应，TCP 保活时间就重置了。
- 如果客户端宕机，服务器间歇发完 9 次探测报文都没有收到客户端的响应就会断开连接。

## (十一) TCP Fast Open

- 第一次建立 TCP 连接时，带上 Fast Open 选项且 Cookie 为空，服务器会生成 Cookie，并返回给客户端，客户端会缓存该 Cookie。
- 从第二次 TCP 连接开始，客户端发起请求带上 Cookie；只要 Cookie 有效，服务器就可以从第二次握手开始带上数据，并且不用等待 TCP 的第三次握手就可以接着发送数据。

## (十二) TCP 的缺点

1. TCP 升级困难，需要客户端和服务端同时支持才可以，并且 TCP 协议升级需要升级内核。
2. TCP 建立连接延迟很大：
3. TCP **队头阻塞**问题：TCP 基于字节流，如果序列号较低的报文丢失，后续报文即使已经接收了，应用层也无法从内核的缓存中读取这些数据。最终导致应用层请求被阻塞。
4. 网络迁移需要重新建立 TCP 连接：TCP 通过四元组唯一确定一个 TCP 连接，如果网络发生变化导致 IP 地址变化，就要重新建立连接。

### 1. HTTP 请求方法

| 方法     | 含义                                         |
| ------ | ------------------------------------------ |
| GET    | 从服务器获取指定的资源。只读操作，安全且幂等。GET 操作的结果可能会被浏览器缓存。 |
| POST   | 根据请求报文对指定的资源做出处理。                          |
| PUT    | 向服务器更新指定资源，通常用于更新已存在的资源。                   |
| DELETE | 请求服务器删除指定资源。                               |
| HEAD   | 类似于 GET，用于获取资源的头部信息而不获取实际内容。               |

### 2. HTTP 常用状态码
![[HTTP 状态码.jpg]]
1. 301 和 302 都会使用 **Location** 字段指明后续要跳转的 url。
	- 301 表示永久重定向，浏览器会缓存新的 url，后续请求浏览器会直接使用新的 URL 方法。
	- 302 表示临时重定向，浏览器每次都会访问原始 url。
2. 400 可能是语法错误、参数错误、JSON 格式错误、缺少字段等。
	- 401 表示未认证或 token 过期或失效；403 表示认证成功但是权限不足。
	- 404 表示请求路径不存在。
	- 405 表示请求方法不正确。
3. 502 表示网关或者代理服务器执行请求，从上游受到无效响应。
	- 504 表示网关或者代理服务器执行请求，已经超时了还没有收到响应。

### 3. HTTP 短连接与长连接
- HTTP 协议采用的是**请求-应答**模式，也就是客户端发起了请求，服务端才会返回响应。
- **短连接**中每次请求与相应都要经历：**建立 TCP 连接 -> 请求资源 -> 响应资源 -> 释放 TCP 连接**的过程。
- **长连接**在请求头部设置 **Keep-Alive** 字段，实现一次 TCP 连接、多次 Http 请求与应答。降低建立和释放 TCP 连接的开销，提高性能。

### 4. HTTP 长轮询
- 客户端发起请求后，如果有数据立即返回；如果没有数据，不会立即返回无数据，而是**挂起客户端请求并保持一段时间连接**。
- 如果在此期间内，有数据可以返回就立即返回给客户端。实现了一种看起来像是服务器主动推送的功能。

## (三) HTTP 1.1
### 1. 默认长连接
- Http 1.0 长连接默认关闭，Http 1.1 长连接默认打开。
### 2. 拆包
- 通过在请求头部设置 **Content-Length** 字段表示报文中有多少字节数据。
### 3. 断点续传
- 客户端发起请求，服务器在响应报文头部设置 **Accept-Ranges: bytes** 告诉客户端自己支持 Range 请求。
- 如果客户端通信过程中网络断开了，可以通过在请求头部设置 **Range:bytes=开始-结束**字段，告诉服务器从开始位置继续传输资源。
- 服务器会从该位置开始传输，并在响应头部中设置 **Content-Range:bytes**、**Content-Length** 字段。
### 4. 应用层的队头阻塞问题
- Http 1.1 仍采用请求-响应模式，虽然客户端可以连续发送多个请求，但是客户端在等待前面的请求的响应的过程中，无法处理已到达的后续请求的响应。

## (四) HTTP 2.0

### 1. 头部压缩

- Http 1.1 的请求头部包含很多固定字段，且头部经常在多个请求中保持不变，浪费带宽。
- Http 2.0 采用 HPACK 算法，主要包括
	- **静态编码表**：固定的 61 个静态索引和请求头字段映射表。
	- **动态编码表**：在通信过程中，动态缓存的头部字段。
	- **哈夫曼编码**：使用哈夫曼编码对所有不在编码表中的 value 进行编码。

### 2. 二进制分帧

- Http 2.0 将文本格式改成二进制格式，提高了传输效率。Http 帧头部只有 9B，前三个字节表示帧数据长度，类型字段将帧分为数据帧和控制帧。

<img src="00-resource/images/HTTP2 帧格式.webp" style="zoom:60%;">

### 3. 多路复用+并发传输
- Http 2.0 中，多个 **Stream** 可以复用一条 TCP 连接。
- Stream 是**双向、独立、有序的帧序列**，同一个 Stream 内的帧按序发送，不同 Stream 的帧可以乱序发送，从而实现基于 Stream 的并发传输。
- 客户端发起的请求必须使用奇数号 Stream，服务器发起的请求必须使用偶数号 Stream。
- 一个 Stream 对应一个完整的 Http 请求和响应，包含多个 Message，一个 Message 就是一条请求或响应。每一个 Message 由若干个帧组成，一个二进制帧可能由多个 TCP 报文组成。

### 4. 服务器推送（Server push）
- Http 2.0 支持服务器主动推送资源，而不用等到客户端主动发起请求。服务器主动推送资源时，通过特定的控制帧，并使用 **Promised Stream ID** 告诉客户端接下来在这个 Stream 中发送资源。

## (五) QUIC 协议
- QUIC (Quick UDP Internet Connections) 是基于 **UDP** 实现的**可靠传输**协议，没有应用层和传输层的队头阻塞、更快的连接建立、支持连接迁移。
- **UDP 报文 = UDP 报头 + (QUIC 报头 + (QUIC 帧头部 + (Http 3 帧头部 + Http 3 帧负载)))**

### 1. 可靠传输
- QUIC Packet Header 分为首次**建立连接的 Long 报头**、**传输数据的 Short 报头**。
	- QUIC 通过三次握手建立连接，确定 **Connection ID**，后续传输只要固定连接 ID 从而实现连接迁移功能。
	- Short 报头中的 **Packet Number** 字段是严格递增的，即使是重传报文序号字段也不一样。避免了重传的歧义问题，使得 RTT 的计算更加准确。且支持乱序确认。
- 一个 QUIC 报文中可以存放多个 QUIC 帧。
	- QUIC Frame Header 中存在 **Stream ID** 和 **Offset** 字段，搭配 **Packet Number**，可以支持乱序确认的同时能够正确组装重传数据。

### 2. 流量控制
- QUIC 是基于 UDP 的，而 UDP 没有流量控制，因此 QUIC 协议自己实现了**滑动窗口**协议。通过控制帧通知发送方自己的接收窗口大小以及是否阻塞等。
- QUIC 给同一个连接上的多个 Stream 分配**独立的滑动窗口**，不同 Stream 之间互相独立，一个 Stream 阻塞不会影响其他 Stream，从而解决了**队头阻塞问题**。
- 每个 Stream 单独进行流量控制，整个连接也有控制。

### 3. 连接迁移
- QUIC 通过**连接 ID** 唯一确定通信双方。当发生网络变化导致 IP 变化时，只要保留上下文信息（连接 ID、TLS 密钥等）就可以复用原连接。

### 4. 更快建立连接
- QUIC 协议内部包含了 TLS 协议，TLS 建立连接时帧中会携带 TLS 信息，且 QUIC 使用的是 TLS1.3。初次建立连接只需要 **1RTT** 就能一起完成建立连接与密钥协商，后续连接应用数据可以和 QUIC 握手信息一起发送，只需要 **0-RTT**。

## (一) TLS 握手过程

1. 客户端发起 ClientHello 请求，发送自己的 **TLS 版本**、**Client Random**、支持的**加密算法**列表给服务器。
2. 服务器发送 ServerHello 响应，确认 TLS 版本、**Server Random**、确认的加密算法，然后发送自己的**数字证书**。
3. 客户端用 Hash 算法计算数字证书的哈希值 H1，然后用 CA 公钥解密服务器数字证书得到哈希值 H2，比较两个哈希值，如果相同则可信。然后取出服务器的**公钥**，用公钥加密**对称密钥**发送给服务器，并发送**加密算法改变通知**，表示后续通信都使用会话密钥加密。然后发送客户端**握手结束通知**且发送**摘要**。
4. 服务器利用**私钥**解密得到**对称密钥**。服务器也发送**加密算法改变通知**，以及**服务器握手结束通知**和**摘要**。

## (二) HTTPS 防止中间人攻击

1. **身份验证**

- 服务器持有 CA 颁发的数字证书，客户端会验证数字证书的有效性。
- 客户端用服务器的公钥加密将要发送的数据，攻击者无法获取服务器的私钥，就无法解密客户端的数据。

2. **非对称加密**

- 通过非对称加密协商对称密钥，后续所有通信都用对称密钥加密，攻击者无法解析内容。

3. **消息完整性校验**

- https 传输的数据都携带消息验证码 MAC，任何对消息的修改都会导致消息验证失败。

# 七、SSE (Server-Sent Events，服务器推送事件)

- SSE 是 HTTP 标准的一部分，客户端发起一个请求后，服务器使用 **EventSource** API 保持连接不关闭持续向客户端推送数据。
- 服务器在 Http 头中使用 `Content-Type: text/event-stream` 表示该响应是 SSE 流。

## (一) SSE 事件中不同的行
1. 重连间隔行 `retry:`，服务器用来通知客户端连接断开多长时间尝试重连。一般只在连接建立后**发送一次**。
2. 事件 ID 行 `id:`，用来支持断线重连。客户端重连时在 Http 请求头带上 `Last-Event-ID:`字段标识已经收到的最后一个事件 id，服务器自动从断开的地方重传。
3. 事件类型行 `event:`，默认为 **message** 类型，可以设置为自定义类型。
4. 事件数据行 `data:`，一个事件可以有多行 data，用换行符 `\n`隔开。
5. 注释行 `:`，注释行会被客户端直接忽略，可以用来实现 Http 连接的**心跳保活**。

## (二) 事件结束
- 同一个事件中可以包含上述不同的行，行与行之间用换行符 `\n`隔开。
- 事件与事件之间用连续**两个换行**即一个空行分隔，读取到空行就说明当前读取的事件已经结束。

# 十、身份凭证方案

- 登陆成功，服务器下发凭证。
- 后续请求，客户端都要携带凭证。
- 服务器验证凭证，确认登录状态有效。

## (一) Cookie + session（有状态）

- 用户登录后，服务器生成 Session，存储用户信息，然后将 SessionID 返回给用户。
- 浏览器将 SessionID 存储在 Cookie 中，后续请求携带 Cookie。
- 服务器拿到 SessionID，然后 Session 中查询用户信息，查到了就表示用户已登陆，否则未登录。

## (二) Redis 存 token（有状态）

- 服务器生成一个 token，存储到 Redis 中，然后把 token 返回给前端。
- 客户端每次请求都带上这个 token，服务器查询 redis 中是否存在该 token。
- **过期时间**：token 必须要设置过期时间，用户持续访问就顺带刷新过期时间。只有长时间不操作，token 才会过期。

## (三) JWT (Json Web Token)（无状态）

- JWT 本身是明文传输，只能保证数据的完整性，但不能保证安全性，安全性依赖于 https 防窃听。
- 服务器只需要校验签名、检查过期时间、解析用户 ID 既可获得用户身份。
- 优点：服务端压力小、扩展简单、适配分布式。
- 缺点：服务器无法主动使 JWT 失效，如果 JWT 泄露，攻击者就可以在 JWT 过期之前冒充用户访问系统。

### 1. 字段

- **头部**（Header）：声明类型和签名算法，用 Base64 序列化。
- **载荷**（Payload）：负载数据，包括：签发者、主题、过期时间戳、自定义内容等，用 Base64 序列化。
- **签名**（Signature）：使用头部中声明的算法，头部和载荷对进行签名得到的结果。

## (四) 双 token 方案 (Access token + Refresh token)

- Access token 用来访问接口，过期时间短。即使泄露，攻击窗口也很短。
- Refresh token 用来刷新 Access token 以及最终确定用户登陆状态。服务器删除 Refresh token，即使用 Access token 也无法访问系统。
- Refresh token 一般存储在服务器（如 redis）。

# 十一、REST API

- REST (Resource Representational State Transfer) 资源表现形式状态转换。核心思想就是一切皆**资源**，然后通过 HTTP 的方法操作资源，使资源以某种**表现形式**发生**状态转移**。
- REST API 本质上就是基于 HTTP 的 API 设计风格，核心目标是使得 **API 语义清晰、风格统一**，开发者即使不看文档也能知道 api 的语义。
- **资源（Resource）**：每一个 URI（统一资源标识符）代表一个资源。
- **表现形式（Representational）**：客户端和服务器之间，传递这种资源的某种表现形式比如 json、xml、image、txt 等等。
- **状态转移（State Transfer）**：Http 协议是一种无状态协议，但是客户端通过特定的 HTTP 方法，对服务器端资源进行操作，实现"表现层状态转化"。

### 1. 动作
- **GET**：请求从服务器获取特定资源。举个例子：GET /classes（获取所有班级）
- **POST**：在服务器上创建一个新的资源。举个例子：POST /classes（创建班级）
- **PUT**：更新服务器上的资源（客户端提供更新后的整个资源）。举个例子：PUT /classes/12（更新编号为 12 的班级）
- **DELETE**：从服务器删除特定的资源。举个例子：DELETE /classes/12（删除编号为 12 的班级）

### 2. 路径
- 路径又称"终点"（endpoint），表示 API 的具体网址。

# 十二、CDN（Content Delivery Network，内容分发网络）

- CDN 是一种**分布式服务器网络**，核心思路就是把内容缓存到**离用户最近的边缘节点**上，让用户就近获取数据，而不是每次都跑到源站（origin server）去拿。
- CDN 的边缘节点本质上就是一个**反向代理缓存服务器**，它拦截用户请求，如果本地有缓存且未过期就直接返回。如果没有，边缘节点代替客户端房屋内源站，然后将资源缓存在本地，最后返回给用户。

# 十三、反向代理和正向代理

## (一) 正向代理（代理客户端）

- 客户端将请求发给代理，然后代理访问目标服务器，将结果返回给客户端。目标服务器只知道是代理在请求，不知道真正的客户端是谁。

### 1. 使用场景

- 访问被墙的网站（翻墙/科学上网）。
- 企业内部统一出口上网，进行流量控制和审计。
- 缓存公共资源，加速内网访问。

## (二) 反向代理（代理服务端）

- 客户端以为自己访问的是目标服务器，实际上所有请求都有代理服务器接收，然后代理服务器根据负载均衡、缓存等策略将请求分发到后台服务器。

### 1. 典型场景

- 负载均衡（Nginx 分发请求到多台应用服务器）。
- SSL 卸载（HTTPS 终结在代理，后端用 HTTP）。
- 安全防护（隐藏内部服务器 IP，防 DDoS）。
- CDN 静态资源缓存和压缩。
