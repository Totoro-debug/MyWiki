## Agent 核心模块

### 1. 工具调用
- 工具是 Agent 和外部世界交互、执行任务的唯一入口。
- 核心思想是**决策和执行分离**，大模型输出调用工具、执行命令的决策，然后由工程代码负责执行，大模型本身不能直接调用工具。

### 2. 记忆系统
- LLM 记忆只局限于上下文窗口，而 Agent 的记忆分为短期和长期记忆，能在交互中保持上下文，并从历史经验中学习。
- 短期记忆就是工作记忆，主要记录用户输入、任务执行状态等。
- 长期记忆保存用户偏好、历史记录，常见方案有：文件、向量数据库、知识图谱。

### 3. 规划执行
- Agent 具备将复杂任务拆解为可以管理和定性的子任务，可以根据任务制定执行计划，执行任务的过程中具备纠错和反思的能力。

# 一、工具调用

- **Tool** 对 LLM 来说就等于是 **Tool Schema** 形式封装的函数，都有输入、输出、处理过程。在 Agent 中，由大模型决定是否调用 Tool；在 Workflow 中，由程序员决定编码决定是否调用 Tool。

## (一) Function Call / Tool Use
- **Function Call** 核心是让大模型根据用户的请求，判断是否需要调用函数/工具。如果模型判断需要调用工具，则输出一个**结构化的响应** (如 **JSON Schema**)，一般包含**函数名**和**参数**，由 **Agent 执行函数**并将结果返回给模型，模型基于结果生成最终答案。
- **Tool Schema** (工具结构定义)
	- 定义工具的名称、参数、功能描述等，模型对工具的所有认知都来自于 Tool Schema。
	- 渐进式披露：首先向模型暴露**元数据** (名称、什么时候使用)，模型决定调用工具后才读取完整的定义。
- **Tool Selection** (工具选择)
	- Tool Schema 中对工具的定义必须清晰明确。
	- 工具数量不要太多，工具职责单一、界限明确。
	- 工具分组、分层架构。
	- 工具执行出错，错误信息必须对大模型来说容易理解。

## (二) MCP (Model Context Protocol)
- MCP 使用 **JSON-RPC 2.0** 通信协议让大模型通过**统一的接口**使用工具、数据源、Prompt 等。MCP 解决了每个 AI 应用接入外部工具都要单独写代码的问题，将 **N×M** 套代码减少为 **N+M** 套代码：每个应用只要实现一个 MCP Client，每个服务只要实现一个 MCP Server。
- MCP 的意义在于：减少重复代码、统一能力接口。

1. MCP 架构
	- **MCP** **Host**：使用 MCP 调用工具的应用，如：Claude Code、自定义 Agent 应用等。
	- **MCP** **Client**：属于 Host 一部分，负责与 MCP Server 进行通信。
	- **MCP** **Server**：轻量级服务器，每个 Server 提供一组服务，通过 MCP 协议和 Client 交互。

2. MCP 能力
	- **Tools**：相当于 Function Call，由模型决定是否调用，只是将工具定义从 Client 端转移到 Server 端。
	- **Resources**：由 Agent 应用或者用户决定读取什么资源，然后将结果作为上下文提供给模型。
	- **Prompts**：用来将一些可复用的 Prompt 最佳实践封装成预定义模板。

3. MCP 通信
	- **Stdio 标准输入输出**：MCP Server 作为**本地子进程**运行，Client 启动 Server 进程，然后向 Server 的标准输入写入 JSON-RPC 请求，Server 调用工具后将结果以 JSON-RPC 格式写入 stdout，Client 读取响应。
	- **Streamable HTTP 可流式 Http**：MCP Server 作为一个 Http 服务运行并监听端口，Client 通过 JSON-RPC 发起 Http 请求，Server 处理请求返回 Http 响应，可以选择通过 **SSE** 返回结果。

# 二、记忆系统

- Agent 通过记忆系统解决了三个关键问题：① **多轮对话**、② **任务连续性**、③ **个性化**。

## (一) 短期记忆

- 短期记忆存储历史会话、工具调用结果，是维持会话连续性、执行复杂任务的基础。

### 1. 全量上下文

- 将最近的对话轮次全部加入 prompt，信息保留完整。但是内容越来越多，可能会超出上下文窗口限制，导致发生截断。LLM 的使用推理成本和输出延迟增加。

### 2. Token 阈值截断

- 给历史对话设置 Token 上限，从最新的消息计算，超出 Token 的消息直接丢弃。

### 3. 滑动窗口

- 只保留最近的 N 轮对话，更早的对话主动舍弃。可以控制成本，并提升推理速度。但是会丢弃早期的信息，影响模型输出的准确性。

### 4. 摘要压缩

- 用大模型将早期对话压缩成摘要，保留关键信息。
- 触发策略：固定轮数、Token 阈值、话题切换、主动判断。

### 5. 重要性过滤

- 给对话记录打一个重要性分数，低于阈值的优先淘汰。
- **观察遮蔽**：不删除低分内容，而是在构造 prompt 时选择性地隐藏历史内容。所有历史信息不会被真的删除，而是在不同阶段被有选择地加入 prompt。

### 6. 结构化工作记忆

- 结构化工作记忆思路是不再将历史信息、工具调用结果等以原始状态保存，而是结构化组织
- 是将记忆划分为几个固定的区域，例如：任务目标、子任务执行状态等。

## (二) 长期记忆

- 长期记忆只存储能帮助 Agent 提升性能的内容，如：用户偏好和习惯、任务执行中产生的失败教训或可复用的成功经验、外部文档或知识等。

### 1. 怎么存

- 检测到用户使用“记住”等关键字、或者识别出重要事实如：项目名等。
- **关系型数据库/ES**：存结构化数据，特别是用户偏好、重要配置等适合**关键词匹配**的数据。
- **向量数据库**：文档、FAQ、特殊事实等适合用**语义匹配**的数据。

### 2. 怎么读/什么时候读

- **主动检索**：每个任务开始前，提取关键词或转换为向量主动检索相关知识。
- **被动触发**：将查询长期记忆封装为 Tool 或 Skill，让 Agent 自己决定什么时候调用。
- 最佳实践：在任务开始时主动查询一次，后续由模型判断是否需要查询外部知识或者用户偏好等。

### 3. 记忆衰减

- 人类的记忆会随时间遗忘，Agent 的长期记忆也应该由类似机制，特别是关于同一方面的多条记忆，越靠近现在的记忆相对来说越重要越可信。
- 为每条记忆增加一个新鲜度权重、或有效期窗口，检索时同时考虑语义相似度和新鲜度。
- 定时检查长期记忆，将重复记忆、过期记忆删除或合并。

# 三、Workflow 编排模式

### 1. Prompt Chaining 提示链

- 把一个大任务拆成多个小步骤，前一步的输出作为后一步的输入，按固定顺序执行。

### 2. Routing 路由

- 用一个 LLM 做意图识别，根据意图把请求路由到不同的分支，不同的分支有不同的处理流程。
- 例子：客服系统。

### 3. Parallelization 并行化

- 把可以同时进行的子任务并行执行，最后汇总结果，这在需要多维度分析的场景下特别有用。
- 例子：同时从多个数据源检索信息。

### 4. Orchestrator-Workers 编排者-工人

- 编排者负责分配任务，多个 Worker 各自完成子任务。适合任务可以分解但子任务之间相互独立的场景。

### 5. Evaluator-Optimizer 评估者-优化者

- 一个 LLM 负责生成输出，另一个 LLM 负责评估这个输出的质量。如果评估不通过就把反馈给到生成者，让它改进后重新输出，如此循环直到评估通过或者达到最大重试次数。
- 这个模式适合对输出质量要求很高的场景，比如生成营销文案、撰写法律条款、编写代码等。

# 四、Agent 设计范式

## (一) ReAct（Reasoning + Act）

- ReAct 核心就是“**推理 Reasoning + 执行 Act + 观察 Observation**”的循环，根据当前状态推理协议推理下一步该做什么，执行完成后，观察执行结果。重复循环直到模型判断任务已经完成/解决了用户的需求，此过程中，推理和执行是交替进行的。
- ReAct 中模型只负责思考，然后输出工具调用信息或输出最终结果。整个 ReAct 的循环流程以及循环终止检测由 Agent 中的代码控制。
- **优点**

- 推理阶段可以显著提升任务成功率。
- 推理的输出使得执行具备可解释性。
- ReAct 具备动态规划的能力。

- **缺点**

- ReAct 是推理执行交叉，每一步都是局部最优策略，但没有全局规划，可能无法完成复杂任务。
- ReAct 可能在中间阶段陷入死循环，或者反复在某些子任务之间来回执行。
- ReAct 高度依赖外部工具和 Skill 的稳定性和性能。
- ReAct 会导致任务响应延迟增加，Token 的消耗也会增加。

### 1. 如何解决 ReAct 死循环？

- **最大步数限制**——通常设 15 步，超过就强制终止。
- **重复动作检测**——连续 3 次调用同一个工具且参数相同，直接退出循环。
- **超时控制**——整个任务设置最大执行时间。

## (二) Plan-and-**Execute**

- 将规划和执行拆分为两个独立的阶段。大模型先制定全局计划，将任务拆成多个子任务，然后另一个 LLM 按照计划逐步执行。
- **缺点**

- 偏向静态规划，不具备动态调整的能力，如果中间结果和预期不符，整个计划可能都不合适。

### 1. 动态重规划

- 每次执行完一步后，将结果反馈给规划器，规划器判断当前结果是否符合预期，如果不符合，规划器需要重新规划当前步骤和后续计划，然后重新执行，甚至回滚。

## (三) Reflection

- Agent 完成任务后，让模型或另一个模型对结果进行检查，根据检查结果修正答案或重新执行任务。赋予 Agent 自我纠错与迭代优化的能力，尤其在代码生成、文档写作等场景效果特别明显。

### 1. **Reflexion 变体**

- Reflexion 不仅需要模型判断结果是否符合预期，还要求在执行出错时生成反思总结，记录失败的原因和改进建议，然后将这个总结作为额外的上下文传给下一次重试。

## (四) Agentic Workflow

- 纯 Agent 不确定性太高，行为不可控，纯 Workflow 不够灵活，因此最实用的做法就是：整体架构用 Workflow 确保可控性，灵活性要求高的局部用 Agent 保证灵活性。
- Anthropic 在工程博客里总结了一个实用的原则：**能用 Workflow 解决的问题，就不要用 Agent**。

# 五、Multi-Agent

## (一) 单 agent 有什么问题

- 上下文窗口限制，单 agent 处理所有任务，复杂信息量太多，会导致上下文撑爆、成本增加、上下文腐烂等问题。

## (二) 多 Agent 设计

### 1. 中心化方案

- 核心在于拥有一个名为**编排器 Orchestrator** 的角色，它负责理解用户需求、解析任务目标、拆分并分配子任务等。
- **静态规划**：任务拆分与分配规则是预定义的工作流，例如：代码交给 Coding Agent、搜索交给 Search Agent 等。
- **动态规划**：动态规划的编排器一般是一个单独的 Agent，利用大模型理解需求、拆分任务等，动态重规划也是由 LLM 进行的。

### 2. 去中心化方案

- 核心思路是没有一个核心的调度者，而是多 Agent 之间通过消息队列、共享内存等自行通信和协商。
- 去中心化理论上很灵活、没有单点问题，但是实际工程上存在很多不可用的缺点：

- 子 Agent 处理任务时可能会进行重复操作。
- 如果任务之间有依赖，下游 agent 不知道什么时候上有 agent 才能做完，也不知道要等哪些 agent 处理完任务。
- 如果子 Agent 执行任务出错，整个系统最后可能得到一份不完整的结果。

# 六、Harness Engineering

## (一) Skill
- Skill 是一个**结构化**的、**可复用**的、**封装**好的包/目录。最基本的 skill 只包含一个 `SKILL.md`。
### 1. Skill 的结构
1. `SKILL.md` 是必须的文件，由 **元数据 + 正文** 组成。
	- 元数据使用 YAML Frontmatter 格式，指明 Skill 的名称和描述 (什么时候使用该 Skill)。
	- 正文正常的 Markdown 格式，一般包含：Skill 的作用、使用场景、工作步骤、使用约束等等。
2. `scripts` 一些可执行脚本，在 Skill 工作过程中使用这些脚本完成指定任务。
3. `references` 一些参考资料，用给 LLM 补充背景或者提供约束。
4. `assets` 一些资源，例如：模板、icon 等。

### 2. Skill 的价值
- **渐进式加载**：从 元数据 -> 正文 -> 按需加载的脚本和资源，渐进式加载 + 按需加载的好处在于：
	1. 可以极大的节省 token。
	2. 减少对上下文的占用，也减少对模型注意力的干扰。
- **复杂工作流的复用**：将一套实用的工作流沉淀下来，可以很轻易的移植给其他人/团队使用。

## (二) A2A 协议

- A2A 协议解决的是 agent 之间的通信和协作问题。
- **Agent Card**：每个 Agent 发布一个 Json 描述文件，描述自己的名称、能力、位置、认证方式等。

 系统提示词；
- 项目规范；
- 工具集；
- 隔离的执行环境 (如：沙箱) 与权限管理；
- 上下文管理；
- 模型调用；
- Sub-Agent 的管理与协调。

- 规则层：定义 Agent 执行约束，包括：代码规范、安全策略、访问权限等。
- 记忆系统：通过结构化方式记录历史信息，例如：任务进度、关键决策、已有结果等。
- 技能：将一些标准化流程抽象为技能，agent 根据需要使用已有技能。
- 验证：主要包含 CI/CD 即持续集成、持续交付，通常包含：Lint (静态代码分析)、测试、修复、重新部署等。
