# 一、执行引擎

- 执行引擎负责将字节码指令解释/编译为对应平台上的本地机器指令。

1. **为什么说 Java 是半编译半解释型语言**

- JVM 在执行字节码时，既可以解释执行，也可以编译执行，而且通常将二者结合使用。

2. **设置 JVM 执行方式**

- `-Xint`：完全采用解释器执行。
- `-Xcomp`：完全采用 JIT 执行。如果 JIT 出现问题，解释器可以介入执行。
- `-Xmixed`：HotSpot VM 默认采用解释器 + JIT 的**混合模式**执行。JVM 启动后，首先由解释器执行代码；随时间推移，JIT 编译器通过热点探测功能，将热点代码的字节码编译为机器码并缓存。

## (一) 解释器

- 按规范将字节码**逐行翻译**为硬件支持的机器码，并立即执行。

### 1. 字节码解释器

- 通过纯软件代码模拟字节码执行。

### 2. 模板类解释器

- 将每一条字节码和一个模板函数关联，模板函数可以直接产生对应字节码的机器码。
- HotSpot 中，解释器主要包括：① `Interpreter` 实现解释器的核心功能；② `Code`用于管理 HotSpot VM 在运行时生成的机器指令。

## (二) JIT 编译器（Just-In-Time）

- `Client Compiler`也称 C1 编译器，32 位机器默认使用，可以通过`-client`手动开启。C1 编译器会进行简单和可靠的优化，耗时短，编译速度快。
- `Server Compiler`也称 C2 编译器，64 位机器默认使用，可以通过`-server`手动开启。C2 编译器会进行耗时长的优化以及激进优化，优化的代码执行效率更高。

- C2 编译器基于**逃逸分析**进行标量替换、栈上分配、锁消除等优化。

### 1. 热点代码

- 一个被多次调用，或方法体内循环次数较多的循环体都可以称为热点代码。
- 对于方法，从解释执行变为编译执行是在两次方法调用之间进行的。
- 对于循环，在循环入口处判断是否已经编译为机器码，不用等待方法结束，称为**栈上替换（On Stack Replacement，OSR）编译**。

### 2. 热点探测

- HotSpot VM 采用基于**计数器**的热点探测，为每一个方法建立 2 个不同类型的计数器：方法调用计数器（Invocation Counter）、回边计数器（Back Edge Counter）。
- **方法调用计数器**：用于统计方法在一段时间内被调用的次数，触发 JIT 编译的默认阈值在 Client 模式下是 1500，Server 模式下是 10000 次。通过`-XXCompileThreshold`设置阈值。

- 方法被调用时，检查是否存在 JIT 编译的代码缓存，若存在，则执行该代码缓存。否则，调用计数器 +1。如果此时方法调用计数器达到上述阈值，则请求进行 JIT 编译，编译后的代码缓存放在方法区的 Code Cache。
- **热度衰减**

- 如果当时间超过**半衰周期**后，调用次数还是达不到阈值，则在**进行 GC 时**方法调用计数器会减少一半。
- `-XX:-UseCounterDecay`：设置关闭热度衰减。
- `-XX:CounterHalfLifeTime`设置半衰周期的长度，单位秒。

- **回边计数器**：统计循环中循环体执行次数。

- 当遇到回边指令时（循环起始位置），检查是否存在 JIT 编译的代码缓存，若存在，则执行该代码缓存。否则，回边计数器 +1。如果此时回边计数器达到阈值 20000，则向 JIT 提交 OSR 编译请求，编译后的代码缓存放在方法区的 Code Cache。

### 3. 逃逸分析

- 逃逸分析只在 Server 模式中支持，用`-XX:+DoEscapeAnalysis`设置开启逃逸分析。

1. **全局逃逸**

- 对象作用范围超出方法或线程。如：静态变量、方法返回值。

2. **参数逃逸**

- 对象作为参数或被参数引用，但在方法调用期间不会全局逃逸。

3. **无逃逸**

|   |   |   |   |
|---|---|---|---|
||全局逃逸|参数逃逸|无逃逸|
|方法内联|√|√|√|
|循环优化|√|√|√|
|锁消除|×|√|√|
|栈上分配|×|×|√|

### 4. 栈上分配 & 标量替换

- 标量指无法再分解为更小的数据的数据，Java 中指基本数据类型。
- 经过逃逸分析，如果变量没有逃逸，并且可以拆解为标量，那么就可以进行栈上分配。将对象拆为基本数据类型存储在栈中。

### 5. 锁消除

- 如果`synchronized`的锁对象不会被其他线程访问，就可以消除锁。

## (三) AOT 编译器（Ahead Of Time）

- JDK9 引入了静态提前编译器 jaotc，可以在程序运行前将字节码文件转换成 .so 文件，放至生成的动态共享库中。预编译的库可以直接执行，不用再等待 JIT 的预热。
- 破坏了 Java“一次编译，到处运行”的特点，也降低了 Java 链接过程的动态性。

# 二、JVM 生命周期与类加载子系统

## (一) JVM 生命周期

1. **JVM 启动**

- JVM 的启动是通过引导类加载器（bootstrap class loader）创建一个初始类（initial class）来完成的，这个类是由虚拟机的具体实现指定的。

2. **JVM 执行**

- 程序开始执行 JVM 就运行，程序结束 JVM 就停止。

3. **JVM 退出**

- 程序正常执行结束。
- 程序遇见异常或错误终止执行。
- 操作系统出错导致 JVM 终止。
- 某线程调用`Runtime.exit()/halt()`、`System.exit()`，并且安全管理器`SecurityManager`也允许此次操作。

## (二) 类的生命周期

<img src="00-resource/images/Java 类生命周期.png" style="zoom:50%;">

1. **类的加载时机**

- JVM 启动会自动加载核心类、包含 main 方法的类。
- 创建类的实例。
- 访问类的静态成员。
- 通过反射访问类。
- 加载一个类，要先加载它的父类。
- 如果接口中有默认方法，在加载接口的实现类之前，先加载该接口。

2. **类的使用**

- 访问类的静态成员、创建类对象、通过反射获取类的元数据等。

3. **类的卸载**

- 满足以下 3 个条件并且在 FullGC 时，才会从方法区回收该类的 Class 对象。

- 类的所有实例都被 GC 回收。
- 类的 Classloader 被 GC 回收。
- 类的 Class 对象没有强引用。

- JDK 自带的类加载器不会被回收，只有自定义加载器会被回收，所以只有自定义类加载器加载的类可以回收。

## (三) 类的加载过程

### 1. 加载

- 通过**全类名**加载该类字节码文件的二进制字节流，将字节流代表的静态存储结构转化为**方法区**的运行时数据结构。
- 在堆中生成对应的 `java.lang.Class` 对象，作为该类在方法区所有数据的访问入口。

### 2. 连接

1. **验证 Verify**

- 确保字节码文件中的字节流符合虚拟机规范，保证被加载类的正确性。包括：文件格式、元数据、字节码、符号引用验证。

2. **准备 Prepare**

- 为**非 final 的静态变量**分配内存并赋值为默认值。
- **静态常量(static final)** 默认值在编译阶段就已经分配，此阶段中会显式初始化为代码中写的初始值。

3. **解析 Resolve**

- 解析将**运行时常量池**内类、方法、字段的符号引用转换为直接引用的过程。

- **符号引用**是一种通过符号来描述所引用目标的方式，包含全限定名等信息。在编译时，Java 类并不知道所引用类的实际内存地址，因此只能使用符号引用来代替。
- **直接引用**是在运行时使用的引用方式，可以是：直接指向目标的**指针**、相对偏移量、一个间接定位到目标的句柄。

### 3. 初始化

- 初始化就是执行类初始化方法 `<clinit>()` 的过程，只在类首次加载的初始化阶段被调用一次。
- **clinit()** 是 `javac` 编译器自动收集类中的所有**静态变量的赋值**语句和**静态代码块**中的语句按代码先后顺序合并得到的。如果代码中没有这两种语句，字节码文件中就没有 clinit() 方法。
- JVM 会执行父类的 clinit()，再执行子类的 clinit()。
- JVM 会通过线程同步保证 clinit() 在多线程环境下仅执行一次。
- **clinit()** 不同于实例初始化 `init()`，**init()** 在每次创建实例 new 的时候调用。**init()** 包含成员变量的显式初始化、实例化代码块、构造方法。

## (四) 类加载器

- JVM 支持 2 种类加载器：BootStrap ClassLoader 和用户自定义类加载器。其中所有派生于抽象类 ClassLoader 的类加载器都划分为自定义类加载器。
- 已经加载的类会存储在名为 classes 的 ArrayList 中。

### 1. JDK 8 之前

1. **引导类加载器 BootStrap ClassLoader**

- 使用 C/C++ 实现，用来加载 Java 核心库、扩展类加载器和应用程序类加载器，并为他们指定父类加载器。

2. **扩展类加载器 ExtClassLoader**

- 使用 Java 实现，继承自 ClassLoader，父加载器是引导类加载器。
- 负责从 java.ext.dirs 属性指定的目录，或者从 JDK 的 jre/lib/ext 目录下加载类库。用户创建的 Jar 放在该目录下，也由扩展类加载器加载。

3. **应用类加载器 AppClassLoader**

- 使用 Java 实现，继承自 ClassLoader，父加载器是扩展类加载器。
- 负责从 java.class.path 属性指定的目录，或者从环境变量 classpath 下加载类库。
- AppClassLoader 是程序中默认的类加载器，一般应用程序的类都是由它完成。

### 2. JDK 9

1. **引导类加载器 BootClassLoader**

- 使用 C/C++ 实现，用来加载 Java 核心库、平台类加载器和应用程序类加载器，并为他们指定父类加载器。

2. **平台类加载器 PlatformClassLoader**

- 使用 Java 实现，继承自 ClassLoader，父类加载器是引导类加载器。主要加载 JDK 的 lib 目录中除了 java.* 核心类库之外的非核心模块。

3. **应用类加载器 AppClassLoader**

- 使用 Java 实现，继承自 ClassLoader，父类加载器是扩展类加载器。
- 负责从 java.class.path 属性指定的目录，或者从环境变量 classpath 下加载类库。
- AppClassLoader 是程序中默认的类加载器，一般应用程序的类都是由它完成。

### 3. 类加载器的引用

- 如果一个类是由用户类加载器加载的，JVM 会将类加载器的一个引用作为类型信息保存在方法区内。当解析一个类到另一个类的引用时，JVM 需要保证这两个类的类加载器一致。

### 4. 两个 Class 对象为同一个类的必要条件

- 类的全类名必须一致。
- 类的类加载器的实例对象必须相同。

## (五) 双亲委派机制

- JVM 采用按需加载的方式加载字节码文件，只用使用该类时才会将它的字节码文件加载到内存并生成 Class 对象。JVM 采用双亲委派机制进行类加载，即把类加载请求交由父类加载器处理，是一种任务委派模式。
- 可以避免类的重复加载，并且保护核心类不被随意修改。

### 1. 工作原理

- 如果一个类加载器收到了类加载请求，先判断 Class 是否已经加载过。如果未加载，它不会自己直接加载，而是先委托父类加载器加载。
- 如果父类加载器还有父类加载器，则继续向上委托，最终将到达顶层的引导类加载器。
- 如果父类加载器可以完成类加载，就成功返回。否则就让子类加载器自己加载。

### 2. 沙箱安全机制

- 如果程序中自定义核心类，在加载自定义核心类时会优先使用引导类加载器加载，但是引导类加载器在加载过程中会优先加载 JDK 自带的文件，这样就会报错，实现对核心源代码的保护。

### 3. 如何破坏双亲委派机制

- 如果 `ClassLoader.loadClass()` 方法中调用父类加载器的 `loadClass()` 方法加载失败，则调用自己的 `findClass()` 方法完成类加载，保证双亲委派机制。
- 破坏双亲委派机制，需要重写 `loadClass()` 方法，改变优先调用父类加载器的逻辑。

# 三、对象创建/对象实例化

## (一) 对象实例化

### 1. 创建对象的方式

- **new**：某些类、Builder、Factory 的静态方法一般都是 new 一个新对象。
- Class 的 **newInstance()**：反射，但是只能调用 public 的空参构造。
- Constructor 的 **newInstance()**：反射，可以调用任意权限的空参、有参构造。
- **clone()**：需要实现 Cloneable 接口。
- 反序列化
- 第三方库：Objenesis

### 2. 创建对象的过程

1. 判断类是否加载（**加载、链接、初始化 clinit()**）

- 首先检查运行时常量池中能否定位到该类的符号引用，并检查是否加载、链接、初始化。若没有，则通过双亲委派进行类加载。

2. JIT 逃逸分析后，如果没有逃逸可以栈上分配。
3. JIT 没有优化，则在堆上分配。

- **指针碰撞**：内存连续，JVM 维护一个指针分隔已分配内存和空闲内存，移动指针分配内存。
- **空闲列表**：内存不连续，JVM 维护一个空闲列表，找到一个足够大的空间分配内存。
- **并发问题**

- 如果启动了 TLAB 机制，在 TLAB 上分配对象。
- **CAS** 失败重试直到成功、区域**加锁**。

4. 默认初始化，JVM 会将对象的内存空间置为 0 值，保证在没有显式初始化时对象也可以直接使用。
5. 设置对象头。
6. 执行`init()`方法初始化对象。

- **init()** 包含成员变量的**显式初始化**、**实例化代码块**、**构造方法**，最后将对象的引用即对象首地址对应的逻辑地址 return 出去。

## (二) 对象的内存结构

### 1. 对象头

1. **MarkWord** 运行时元数据

- 哈希值 HashCode：指向对象在堆中的首地址。

<img src="00-resource/images/Mark Word64.png" style="zoom:75%;">

2. **类型指针**：指向**方法区**中对象所属类的元数据 InstanceKlass，该指针可以原来判断实例属于哪个类。

- 元数据分为：类元数据 **InstanceKlass**、基本数据类型数组元数据 **TypeArrayKlass**、引用数组元数据 **ObjArrayKlass**。

3. 数组长度：数组对象特有的字段，4B 记录数组容量。

### 2. 实例数据

- 存储代码中的各种字段，包括**本身**和从**父类继承**的字段。

- 父类中的变量在子类变量之前（先加载的父类）。
- 相同宽度的字段被分配在一起。
- 如果 CompactFields 参数为true：子类的窄变量可能插入到父类变量的空隙。

### 3. 对齐填充

- 非必须，起到占位符的作用。

## (三) 对象访问定位

- JVM 通过栈帧上的引用定位到堆中的对象实例。
- 对象访问方式

- **直接指针**（HotSpot）：栈帧中的引用直接指向堆中的实例，然后在实例中由类型指针指向类型数据。
- 句柄访问：栈帧中的引用指向句柄池，句柄池中分别存储实例的指针和类型数据的指针。
- 直接访问访问实例的效率更高，更节约内存。
- 句柄访问栈帧存储句柄地址更稳定，对象移动时指挥改变句柄中的指针，而不需要修改栈帧中的引用。

# 四、运行时数据区

<img src="00-resource/images/JVM 运行时数据区.png" style="zoom:75%;">

- 线程间共享：① 堆；② 方法区/元空间。
- 线程私有：① 程序计数器；② 虚拟机栈；③ 本地方法栈。

## (一) 虚拟机栈

- 虚拟机栈是线程**私有**的，生命周期和线程一致，每一次方法调用都会创建一个栈帧。
- 虚拟机栈不需要进行垃圾回收，可以通过`-Xss`参数设置栈的大小。

### 1. 栈内存与异常

- **固定大小**：线程请求分配的栈超过虚拟机栈允许的最大容量，JVM 会抛出 `**StackOverflowError**`。
- **动态大小**：如果没有充足内存用来扩展虚拟机栈，或创建新线程时创建虚拟机栈，JVM 会抛出 `**OutOfMemoryError**`。

### 2. 栈帧的结构

- 局部变量表 + 操作数栈 + 动态链接 + 返回地址 + 附加信息

1. **局部变量表**

- 局部变量表是一个**数组**，数组中的每个槽可以存 32bit 数据，用来存储方法参数、局部变量、返回值、当前对象引用 this，包括基本数据类型、对象引用（指针、句柄等）。

- 当方法被调用时，方法的参数、局部变量会被按顺序复制到局部变量表中。对于构造方法、成员方法，当前对象引用 **this** 被先存放在下标为 0 的槽处。
- 局部变量表的槽可以复用，新的局部变量可以复用已经过期变量的槽。

- 局部变量表的容量是在**编译时**确定的，方法运行期间不会改变。
- 被局部变量表中直接或间接引用的对象都不会被回收。

2. **操作数栈/表达式栈**

- 操作数栈在方法执行过程中根据字节码指令写入或读取数据，用于保存中间结果。
- 操作数栈的最大容量在**编译时**就确定好，方法运行过程中不会改变。
- 如果方法有返回值，其返回值会被压入操作数栈。
- **栈顶缓存**：将栈顶元素全部缓存到寄存器中，降低内存的读/写次数。

3. **动态链接**

- 动态链接存储的是一个引用，指向该方法所属类的**运行时常量池**。
- 发生方法调用时，通过该动态链接访问运行时常量池，并找到真正的方法，以此支持**多态**的实现。解析成功后，将直接引用**缓存**到常量池中，后续该类的所有栈帧都可以使用该缓存。

4. **返回地址**

- 如果正常退出，返回地址保存的是调用者的 **PC**；如果是异常退出，返回地址要通过异常表来确定，栈帧不保存信息。

### 3. 方法调用

1. **绑定**

- **早期绑定**：在编译期间就能确定具体实现的方法，例如：静态方法、私有方法、final 方法、构造方法、super 调用等。
- **晚期绑定**：在运行时才能确定具体的方法，这依赖于对象的实际类型。

2. **虚方法**

- **虚方法**：可以被重写的方法，非 static、非 final、非 private 的实例方法。
- **非虚方法**：可以在编译期间就确定具体要调用的实现的方法，运行时不可变。

- 静态、私有、final、构造、用 super 显式调用的父类方法都是非虚方法，其余均为虚方法。

- 普通调用指令：invokestatic、invokespecial、invokevirtual、invokeinterface。
- 动态调用指令：invokedynamic。

3. **虚方法表**

- 在类加载的解析阶段，JVM 自动为该类创建虚方法表，并存储在**方法区**。
- 虚方法表首先会被初始化为父类虚方法表，然后用子类重写的方法替换对应虚方法，然后将子类新增的虚方法添加到虚方法表尾部。

## (二) 本地方法栈

- 本地方法栈用于管理本地方法的调用，是线程**私有**的。在 HotSpot 中与虚拟机栈合二为一。
- 本地方法指使用 **native** 修饰的方法，这些方法由非 Java 语言实现，所以没有字节码，而是被编译成动态链接库 (.dll 和 .so)。
- Java 代码调用 native 方法时，JVM 通过 JNI (Java Native Interface) 在本地库中查找函数，然后 JVM 执行本地库中的机器码指令。

## (三) 堆

- 一个进程内的所有线程共享同一个堆，在 JVM 启动时创建。堆占有的内存可以是不连续的，空间大小可以是固定的也可以是动态的。
- 几乎所有**对象实例**以及**数组**都在堆中分配，其中基本数据类型变量随持有它的对象一起被回收。

### 1. 堆的结构

- **堆空间 = 新生代 + 老年代**

- 初始内存默认为物理内存/64，通过`-Xms/-XX:InitialHeapSize`设置。
- 最大内存默认为物理内存/4，通过`-Xmx/-XX:MaxHeapSize`设置。
- 老年代与新生代比例：`-XX:NewRatio`。

- **新生代 = Eden + Survivor0 + Survivor1**

- S0 与 S1 空间大小相等，只能同时使用其中一个，另一个保持空闲。所以新生代的实际可用内存 = Eden + S0/S1。
- 新生代空间大小：`-Xmn`
- Eden 与 Survivor 比例：`-XX:SurvivorRatio`
- 关闭自适应内存分配策略：`-XX:-UseAdaptiveSizePolicy`

- 大对象区

- 某些 JVM 中专门分配大对象的区域。大对象是指需要大量连续内存空间的对象，例如数组等。

### 2. new 对象分配

1. new 的对象默认放 **Eden** 区。如果 Eden 区满或不足，JVM 将使用 `YGC`对新生代进行 GC，不再使用的对象将被销毁。

- Eden、S0/S1 区中剩余对象将被移动到 **S1/S0**，如果 S1/S0 区放不下，直接放到**老年代**。然后设置剩余对象`age + 1`，如果此时 S1/S0 中对象的 age 达到**阈值 15**（CMS 为 6），将被移动到**老年代**。
- 参数`-XX:MaxTenuringThreshold=n`可以设置对象移动到老年代的年龄阈值，区间必须在 0-15。

2. 然后新对象将被放到 Eden 区。如果 Eden 区放不下，则测试老年代是否能放下，如果仍然放不下，则使用 `Major GC` 进行垃圾回收。如果仍然放不下，则抛出 `OutOfMemoryError`。

### 3. 内存分配策略

- 普通对象**优先**分配到 **Eden**。
- **大对象**直接分配到老年代，避免频繁 `Minor GC`产生内存碎片。
- **长期存活对象**分配到老年代。
- **动态对象年龄判断**

- 如果 S0/S1 区中，按照年龄从小到大对对象的大小进行累加，当累加到某个年龄时，累加总和大于 Survivor 区的一半，则取该年龄和预设参数中最小的作为新的阈值。

- **空间分配担保**

- Minor GC 之前，先检查**老年代最大可用连续空间**是否大于新生代所有对象总大小或历次移到老年代的对象的平均大小，如果是，就进行 `Young GC`；否则进行 `Full GC`。

### 4. TLAB（Thread Local Allocation Buffer）

- **快速分配策略**：JVM 在 **Eden** 区为每个线程分配了一块**私有缓存**，默认占 Eden 区的 `1%`，可以通过`-XX:TLABWasteTargetPercent`进行设置。在多线程下可以避免一系列线程安全问题，提升内存分配的吞吐量。
- JVM 将 TLAB 作为堆上分配的**首选**，可以通过 `-XX:UseTLAB`进行设置，如果在 TLAB 中分配内存失败，JVM 就会通过加锁在 Eden 区中分配内存。

## (四) 方法区/元空间

- JDK7 之前是**虚拟机内存中的永久代**，JDK8 开始为**本地内存中的元空间**。
- 方法区由所有线程共享，在 JVM 启动时创建、JVM 关闭时释放。方法区占用内存可以不连续、空间大小可以固定或动态。如果系统加载了太多类，方法区也可能会溢出并抛出 `OutOfMemoryError:Metaspace`。
- 元空间初始内存`-XX:MetaspaceSize`默认 21M，最大内存`-XX:MaxMetaspaceSize` 默认-1 没有限制。当方法去内存不足，就会触发 `Full GC` 并卸载没用的类。如果释放的空间不足，就会增加元空间大小；如果释放空间过多，则降低元空间大小。

### 1. 方法区结构的调整

- jdk6 永久代：① 类元数据、② 方法字节码、③ 常量池、④ 静态变量、⑤ JIT编译后的代码缓存
- jdk7

- 永久代：① 类元数据、② 方法字节码、③ 常量池
- 堆：① 字符串常量池、② 静态变量
- JIT Code Cache：JIT 编译后的机器码缓存，独立于堆之外。

- jdk8：

- 元空间：① 类元数据、② 方法字节码、③ 常量池
- 堆：① 字符串常量池、② 静态变量
- JIT Code Cache：JIT 编译后的机器码缓存，独立于堆和元空间之外。

### 2. 类元数据 InstanceKlass

- 类的全类名、父类的全类名、类的修饰符 (public、abstract、final)、类的直接接口的有序列表。
- 字段的名称、类型、修饰符 (public ...、static、final、volatile、transient) 以及域的声明顺序。
- 方法的名称、返回类型、修饰符 (public ...、static、final、synchronized、native、abstract)、形参的数量和类型（按顺序）。

### 3. 方法字节码

- 方法编译后的字节码。
- 操作数栈及大小、局部变量表及大小（abstract、native 除外）。
- 除 abstract、native 外的方法异常表（异常的开始位置、结束位置、异常处理代码的偏移地址、被捕获异常类在常量池中的索引）。

### 4. 运行时常量池

- class 文件中的常量池：包括**字面量（数值、字符串）**和对**类型、字段、方法的符号引用**。
- 运行时常量池：JVM 为每一个类**分别维护一个常量池**，常量池通过**索引**访问。

### 5. 方法区的 GC

1. **不再使用的类**

- 必要条件

- 该类的**所有实例**都被回收，即堆中不存在该类及其任何派生子类的实例。
- 该类的 **ClassLoader** 实例被回收。
- 该类的 **java.lang.Class** 对象没有**强引用**，无法在任何地方通过反射访问该类的方法。

2. **常量池中废弃的常量**

- 只要常量池中的常量没有被任何地方引用，就可以被回收。

3. **静态变量**

- 与类的 Class 对象一起存放在堆中。只有当类本身被回收时，静态变量才会被回收。

## (五) StringTable

- 字符串常量池本质是一个名为 StringTable 的**哈希表** (数组+链表)，key 是字符串的 HashCode，value 是一个 entry，其中会保存 String 对象的引用。
- `-XX:StringTableSize` 设置 StringTable 的大小。
- **驻留**：当使用字面量或者 intern() 时，创建的 String 对象不是保存在 StringTable 中，而是在堆中创建了一个 String 对象，然后 StringTable 中创建一个对应的 entry 并保存 String 对象的引用。

### 1. String 的内存分配

- 只要**使用字面量**，就会在堆中创建一个对象，并在 StringTable 中**驻留新的或复用**已有的 Entry，然后返回这个 String 对象的引用。
- `**new String()**` 本身只会在堆中创建对象

- `new String("abc")` 使用字面量，首先在常量池驻留或复用对象。然后 **new** 会在堆中创建新对象，new 堆对象的 **value** 数组会直接引用常量池对象的 **value** 数组，即 new 对象和常量池对象内部都引用了同一个 value 数组。
- `new String(String)` 使用已有 String 对象做参数，会在堆中创建新对象，然后新对象的 value 数组会直接引用旧对象的 value 数组，即两个对象内部引用了同一个 value 数组。
- `new String(byte[])` 创建堆对象，然后拷贝参数中的字符/字节数组。

- `**String.valueOf()**` 会调用 **new String() / toString()**。

- boolean 变量返回的是两个预定义的字面量 "true" 或 "false"。
- 基本数据类型调用 toString() 方法，底层还是调用 new String()。
- String 类的 toString() 返回 this，所以 `valueOf(String)` 直接返回原 String 对象的引用。

- **字符串拼接**

- 纯字面量、final 常量：通过编译器直接优化为最终结果，然后在常量池中创建或复用对象，就相当于直接使用字面量。
- 包含变量：底层通过 `StringBuilder` 进行拼接，最后调用`toString()`方法 new 一个 String 对象。并且`StringBuilder.toString()`不会复用字符串常量池中对象，只在堆中创建 String 对象。

### 2. intern()

- 调用 intern() 方法时，JVM 通过 **equals()** 判断字符串常量池中是否存在与当前字符串内容相等的对象。JDK 1.7 及以上，如果常量池中有相同内容 String，直接返回该对象的引用。如果没有，将调用者的引用地址复制一份存到常量池，然后返回原对象的地址。
- intern() 可以确保常量池不同内容字符串只有一个对象，如果程序中存在大量内容重复的字符串，使用 intern() 可以节省内存。
- JDK 1.6

- 如果常量池中有相同内容字符串，直接返回该对象的引用。如果没有，在常量池创建一个新对象，并返回常量池对象的引用。

### 3. StringTable 调整到堆中的原因

- 永久代只有在`Full GC`时才会被回收，而`Full GC`只有老年代或方法区空间不足时才会触发，导致 StringTable 回收效率不高。移到堆中，就能及时回收内存。
- 永久代的默认容量较小，而字符串使用较为频繁，如果大量使用字面量或者 intern() 方法，就容易导致永久代产生 `OutOfMemoryError`。

### 4. 字符串常量池的 GC

- **字面量字符串**：因为运行时常量池中始终有字面量引用这个字符串所以不会被回收，除非类被卸载了导致该类的常量池也被卸载，这种字符串才可能被 gc。
- **intern() 字符串**：当没有地方再使用该字符串时，gc 可以将该对象从字符串常量池中移除并回收。

## (六) 本地内存/直接内存

- 直接内存是 Java 堆外，直接向系统申请的内存空间，访问直接内存的速度优于 Java 堆。
- 来源于 NIO，通过 JNI 分配直接内存，然后通过堆中的 DirectByteBuffer 等对象使用直接内存，避免了 JVM 堆和直接内存之间来回复制数据。
- 直接内存受限于物理内存，超出会报 `OutOfMemoryError: Direct buffer memory` 异常。直接内存大小默认与堆最大值 `-Xmx` 相等，可以通过 `MaxDirectMemorySize` 设置直接内存最大值。

## (七) 引用

### 1. 强引用（Strong Reference）

- 强引用的对象是可触及的，对象只要有强引用，GC 就永远不会回收被引用的对象。
- 强引用可能导致内存泄漏。

### 2. 软引用（Soft Reference）

- 当内存充足时，不会回收仅有软引用的对象。
- 当内存不足时，仅被软引用关联的对象会被加入回收范围进行第二次回收。如果回收后内存仍然不足，则抛出内存溢出异常。
- GC 在回收仅有软引用的对象时，可选地将引用加入`ReferenceQueue`。

### 3. 弱引用（Weak Reference）

- 仅被弱引用关联的对象只能生存到下一次 GC 前。GC 发生时，无论内存是否充足，对象都会被回收。
- GC 在回收仅有弱引用的对象时，可选地将引用加入`ReferenceQueue`。

### 4. 虚引用（Phantom Reference）

- 对象是否有虚引用，完全不会影响对象的生命周期。如果仅有虚引用，随时都可能被GC回收。
- 无法通过虚引用获取被引用的对象。
- 设置虚引用的唯一目的是跟踪垃圾回收过程，在对象被回收时收到一个系统通知。

- 虚引用必须配合`ReferenceQueue`，当 GC 准备回收对象时，如果该对象有虚引用，就会将该虚引用加入引用队列，通知应用程序对象回收情况。

### 5. 终结器引用（Final Reference）

- 用来实现对象的 finalize() 方法，配合`ReferenceQueue`使用。
- GC 时，终结器引用入队，由 Finalizer 线程通过终结器引用找到被引用对象并调用对象的 finalize() 方法，第二次 GC 时才能回收被引用对象。

## (八) 内存溢出

- 没有足够空闲内存，并且 GC 也无法提供更多内存。
- 没有足够空闲内存

- JVM 的堆内存设置不合理。

- 代码中创建了大量大对象，并且长时间不能被 GC 收集（存在被引用）。

- 在抛出 `OutOfMemoryError` 之前，通常会触发 GC，但并不是一定会触发 GC，例如：如果试图分配一个超过堆最大值的超大对象。
- 程序计数器是唯一一个不可能触发 OOM 的区域。

## (九) 内存泄漏

- 对象不再被程序使用但是又存在强引用，GC 无法回收的情况叫内存泄漏。

1. **静态集合类**：Map、List等容器如果是静态的，它们的生命周期与 JVM 一致，容器中的对象在程序结束之前不能被释放，从而造成内存泄漏。
2. **单例模式**：由于单例的静态性质，生命周期和程序一样长，如果单例持有外部对象的引用，外部对象也不会被回收。
3. **内部类持有外部类**：如果外部类的实例方法返回了一个内部类实例对象，并且内部类实例被长期使用，即使外部类对象不再被使用，由于内部类持有外部类对象，外部类对象也不会被 GC。
4. **连接资源**：数据库、网络连接等，需要手动关闭的资源，只有资源被关闭，GC 才会回收对应的对象。
5. **变量的作用域不合理**：如果变量定义的作用范围大于使用范围，就可能导致内存泄漏。如果对象使用完没有及时设置为null，就可能导致内存泄漏。
6. **改变哈希值**：当一个对象被存储在 HashSet 中，就不能修改对象中参与计算哈希值的字段。否则，对象修改后哈希值与原哈希值不同，这样导致无法再从 HashSet 中检索到该对象，进而导致无法删除该对象在 HashSet 中的引用，造成内存泄露。
7. **缓存泄露**：当对象被放入缓存中，就可能导致内存泄漏。
8. **监听器和回调**：客户端在 API 中注册回调，但是没有显式取消，就会导致积累。

# 五、垃圾回收

## (一) GC 的作用/目的

1. 自动管理和回收内存。
2. 提高内存利用率。
3. 降低内存溢出的可能，提高程序健壮性。

## (二) System.gc() / Runtime.getRuntime().gc()

- 在默认情况下，调用 `System.gc()` 会触发 `Full GC` 尝试释放内存。但是 System.gc() 无法保证对垃圾回收器的调用，只是尝试调用。一般情况下，无须手动调用。
- `System.runFinalization()` 强制调用引用对象的 finalize() 方法。

## (三) Stop The World（STW）

- STW 指的是 GC 发生时，整个程序的所有线程都会暂停，没有任何响应。native 方法可以执行但是不能和 JVM 交互。
- STW 是 JVM 在后台自动发起和自动完成的。在用户不可见的情况下，把用户线程全部暂停。
- 可达性分析中枚举根节点会导致所有的 Java 执行线程停顿。

- 分析工作必须在一个能确保一致性的快照中进行。
- 一致性指整个分析期间整个执行系统看起来像被冻结在某个时间点上。
- 如果出现分析过程中对象引用关系还在不断变化，则分析结果的准确性无法保证。

## (四) 安全点与安全区域

### 1. 安全点

- 程序执行时，只有特定的位置才能进行 GC，这些位置称为安全点。通常以“是否具有让程序长时间执行的特征”为标准，选取安全点。
- **抢先式中断**（不再采用）：首先中断所有线程，如果有线程不在安全点，恢复线程执行到安全点。
- **主动式中断**：设置中断标志，线程执行到安全点主动检查标志。如果中断标志为真，线程主动中断。

### 2. 安全区域

- 安全点保证了程序执行时，在不太长的时间内就可以进入GC。但是程序不执行时，例如等待或阻塞时，无法执行到安全点进行中断。
- 安全区域指的是在一段代码中，对象的引用关系不会发生关系，这个区域中任何位置进行 GC 都是安全的。

## (五) Minor GC、Major GC、FGC

- GC日志，详细：`-XX:+PrintGCDetail`，简要：`-XX:+PrintGC/ -verbose:gc`。

1. 新生代 GC（Minor GC/ Young GC）

- 当 Eden 区空间不足时会触发 Minor GC，Survivor 区满不会触发GC。
- Minor GC 会触发 STW，暂停其它用户线程，直到 GC 结束用户线程才会恢复运行。

2. 老年代 GC（Major GC/ Old GC）

- 只有 CMS 会单独 Old GC。老年代空间不足/年轻代晋升到老年代速度过快时，会触发 Old GC。
- 首先进行 Young GC，如果空间还是不足，则触发 Old GC。如果内存仍然不足，则抛出`OutOfMemoryError`。
- Old GC 速度会比 Young GC 慢10倍以上，STW 的时间更长。

3. 混合收集（Mixed GC）

- 只有 G1 会进行混合收集，收集整个年轻代 + 垃圾比例高的老年代 Region。

4. 整堆收集（Full GC）：收集整个堆和方法区。

- 调用 `Sysyem.gc()/ Runtime.getRuntime().gc()` 时，JVM 会尝试执行 Full GC。
- 老年代空间不足。
- 方法区空间不足。
- 空间分配担保失败。
- 大对象直接加入老年代，老年代剩余内存小于大对象的大小。

# 六、垃圾回收算法

## (一) 标记阶段

### 1. 引用计数算法

- 为每个对象保存一个计数器，任何对象引用了当前对象，计数器加1；引用失效时，计数减1。计数器为 0 时，表示对象不可能再被引用。
- 实现简单，回收没有延迟性。
- 时空开销大，无法处理**循环引用**的情况。

### 2. 可达性分析/根搜索算法

1. **根集合**

- 根集合（GC Roots）是一组必须活跃的引用。

- **虚拟机栈**中引用的对象。
- **本地方法栈**内 JNI 引用的对象。
- 方法区中**静态变量**引用的对象。
- 方法区中**常量**引用的对象。
- **synchronized** 锁住的对象。
- JVM 内部的引用：基本数据类型的 **Class 对象**、常驻的**异常对象**、系统**类加载器**。
- 反应JVM内部情况的 JMXBean、JVMTI 中注册的回调、本地代码缓存。
- 除了上述固定的 GC Roots，还可以有其它对象临时性的加入，例如：分代收集和局部收集。

- 如果一个指针，引用了堆中的对象，但是自己不存放在堆中，就是一个Root。

2. **可达性分析**

- 可达性分析就是从根集合出发，从上到下搜索，搜索走过的路径称为**引用链**。如果对象没有任何引用链，就是不可达的。内存中的存活对象都会被根集合直接或间接连接。
- 可达性分析必须在一个能保证一致性的快照中进行，这也是导致 GC 时必须 Stop The World 的一个重要原因。

3. **标记过程**

- 如果对象没有引用链，则进行第一次标记。
- 一次筛选：被标记对象，如果没有重写 finalize() 方法，或者 finalize() 已经被调用过，则不执行 finalize() 方法，对象直接被第二次标记为**不可达**的。如果对象重写了 finalize() 方法并且没有执行过，对象会被插入到 F-Queue 队列中，由低优先级线程 Finalizer 运行该对象的 finalize() 方法。

- 如果对象在 finalize() 方法中与引用链上任何一个对象建立了联系，则对象会被移出 “即将回收” 的集合。
- 如果仍然没有关联，则被第二次标记，只有被第二次标记的对象才会被回收。

4. **finalization 机制**

- GC 回收对象前，总会先调用对象的 finalize() 方法。finalize() 方法允许在子类中被重写，用于自定义对象被回收之前的处理逻辑。
- finalize 会导致 JVM 的不安全、影响 GC 性能，JDK9 开始就被标注为弃用了。
- **不要主动调用 finalize() 方法的原因**

- finalize() 方法可能导致对象复活。
- finalize() 的执行时间没有保证，完全由 GC 线程决定。若不发生 GC，则 finalize() 将没有机会执行。
- 糟糕的 finalize() 会影响GC性能。

5. **虚拟机中对象的三种可能状态**

- **可达的**：从根节点开始，可以到达这个对象。
- **可复活的**：对象的所有引用都被释放，但是对象有可能在 finalize() 中复活。
- **不可达的**：对象的 finalize() 被调用后，仍没有复活，那么就可以被回收。不可达的对象不可能复活，因为 finalize() 只会被调用一次。

### 3. 三色标记算法

- 三色标记法将对象分为三种状态：白色、灰色和黑色。

- **白色**：该对象没有被标记过。在垃圾回收周期开始时，所有对象都是白色。
- **灰色**：该对象已经被标记过了，但该对象的引用的对象还没标记完。
- **黑色**：该对象已经被标记过了，并且他的全部引用对象也都标记完了。

- **初始标记（STW）**：所有对象初始都是白色。遍历 GCRoots，将根对象和直接引用对象标记为灰色。该阶段不用扫描整个堆，时间比较短。
- **并发标记**：从灰色对象开始遍历整个对象图，将被引用的对象标记为灰色，并将已经遍历过的对象标记为黑色。
- **重新标记（STW）**：标记在并发标记阶段中被修改的对象以及未被遍历到的对象。从灰色对象重新开始遍历对象图，将被引用的对象标记为灰色，并将已经遍历过的对象标记为黑色。

## (二) 清除阶段

### 1. 标记-清除算法（Mark-Sweep）

- 当堆中有效内存空间被耗尽时，就会停止整个程序（STW），然后进行标记和回收。
- **标记**：从根节点出发，遍历所有可达对象，并在对象头中记录为**可达对象**。
- **清除**：GC 对堆内存从头至尾进行遍历，如果发现某个对象的对象头中没有标记为可达对象，则将该对象地址保存在空闲列表中。当有新对象需要加载时，判断列表中空闲内存是否足够，如果足够就可以存放。
- 优点

- 速度快，不需要复制、移动对象。

- 缺点

- 清理出的空闲内存不连续，产生大量内存碎片。

### 2. 标记-复制算法（Mark-Copy）

- 将内存**分为两块**，同时只使用其中一块。GC 时将当前区域的存活对象复制到另一块区域，并且更新对象的引用，然后清除当前区域的所有对象。
- 标记-复制算法的效率和存活对象的多少、大小相关，适用于**对象存活率低**的场景，例如**新生代**的 GC。
- 优点

- 实现简单，可以保证内存连续性，没有内存碎片问题。

- 缺点

- 浪费一半空间，内存利用率低。

### 3. 标记-整理算法（Mark-Compact）

- 将所有存活对象移动到内存一端，按原顺序排放，并更新对象的引用。移动完后，将存活对象边界外的内存回收。
- 标记-整理算法适用于**对象存活率高**的场景，例如**老年代**的 GC。
- 优点

- 内存连续，没有内存碎片问题。分配新对象更加方便。

- 缺点

- 需要移动对象并更新对象的引用，效率低，是速度最慢的算法。

### 4. 分代收集算法

- 年轻代：空间小、对象生命周期短、存活率低、回收频繁。

- 一般采用**标记-复制算法**。内存连续便于对象分配，通过 2 个 survivor 区缓解内存利用率低的问题。

- 老年代：空间大、对象生命周期长、存活率高、回收不频繁。

- 一般采用**标记-清除**或**标记-整理算法**。

### 5. 增量收集算法

- 将一次完整的 GC 分为多个小步骤，每次只收集一小片区域的内存，降低单次回收的 STW 时间，GC 穿插在用户线程执行过程中，直到 GC 完成。
- 缺点

- 线程切换和上下文转换的开销，导致 GC 整体效率降低。
- 对象引用关系在回收过程中可能变化，复杂度增加。

### 6. 分区收集算法

- 将堆划分为多个独立的区域 Region，每次回收部分区域而不是整个堆，降低每次回收的 STW 时间。

# 七、垃圾回收器

![](https://cdn.nlark.com/yuque/0/2025/jpeg/46298582/1761483781267-3cd49f48-5a46-4ad4-a726-8554f80280a6.jpeg)

- JDK 9 将`G1`设置为默认回收器，废除了组合`Serial + CMS`、`ParNew + Serial Old`。
- JDK 14 废除了`Parallel Scavenge + Serial Old`，并且删除了`CMS`。JDK 23 将`ZGC`设置为默认垃圾回收器。

## (一) 串行 `Serial + Serial Old`

- Serial 采用 **标记-复制 + 串行回收**，Serial Old 采用 **标记-整理 + 串行回收**。
- Serial 进行垃圾回收时只使用一个 GC 线程，并且必须暂停所有工作线程直到回收完成。
- JDK 8 及之前，Serial 是 HotSpot 在 **Client** 模式下的默认垃圾收集器。`-XX:+UseSerialGC`指定新生代使用 Serial，老年代自动使用 Serial Old。
- 优点

- 实现简单，占用内存少。适用于内存不大、单 CPU 环境。
- 在单线程环境下，没有线程交互与切换的开销，因此比其他 GC 更高效。

- 缺点

- STW 时间长，垃圾回收时间短时可以使用。

## (二) 并行

### 1. Parallel Scavenge + Parallel Old

- Parallel Scavenge 采用 **标记-复制 + 并行回收**，Parallel Old 采用 **标记-整理 + 并行回收**，GC 时暂停所有用户线程。
- Parallel 与 Parallel Old 关注的是**高吞吐量**，适用于 CPU 核心多、用户线程在后台运算而不用太多交互的场景，例如：批处理、工资支付等。
- JDK 8 及之前，Parallel 是 HotSpot 在 **Server** 模式下的默认垃圾回收器。`-XX:+UseParallelGC`、`-XX:+UseParallelOldGC` 开启一个，另一个会自动开启。
- `-XX:ParallelGCThreads`设置新生代并行收集器的线程数。
- `-XX:GCTimeRatio`设置 GC 时间占比 1/(n+1)，取值范围 (0,100)，默认为 n=99 即1%。
- `-XX:MaxGCPauseMillis` 设置垃圾收集最大停顿时间。

### 2. ParNew

- ParNew 采用 **标记-复制 + 并行回收**。
- ParNew 是 Serial 的多线程版本，除了多线程并行回收，几乎没有区别。
- `-XX:+UseParNewGC`指定新生代使用 ParNew，老年代自动使用 CMS。
- `-XX:ParallelGCThreads`设置新生代并行收集器的线程数。

## (三) 并发

### 1. CMS（Concurrent Mark Sweep）

- CMS 采用 **标记-清除 + 并发回收**，`-XX:+UseConcMarkSweepGC` 指定老年代使用 CMS，新生代自动使用 `ParNew`。
- CMS 的重点是**低延迟（停顿时间）**，多线程**并行**进行标记和清除，并且仅在初始标记、重新标记阶段进行 STW。
- 在并发标记、并发清除阶段，用户线程持续运行，CMS 回收时需要保证有足够内存可用。因此，堆内存利用率达到阈值`-XX:CMSInitiatingOccupanyFraction`，就必须主动 GC。GC 过程中，如果预留内存不够用，就会出发`Concurrent Mode Failure`，此时通过启动 `Serial Old`进行 `Full GC` 进行兜底，此时会经历较长 STW。
- `-XX:UseCMSCompactAtFullCollection` 设置在执行完 Full GC 后是否进行压缩整理。
- `-XX:CMSFullGCsBeforeCompaction` 设置执行多少次 Full GC 后进行压缩整理。
- `-XX:ParallelCMSThreads` 设置 CMS 的线程数，默认为 (ParallelGCThreads + 3)/4。

![](https://cdn.nlark.com/yuque/0/2026/png/46298582/1773059514140-44744e0d-166a-400d-b36a-5f6e9fcaf754.png)

1. 回收过程

- **初始标记**：标记出 **GC Roots** 的直接引用对象，**STW** 防止 GC Roots 被修改。
- **并发标记**：从 GC Roots 的直接引用对象出发，遍历并标记所有可达对象。
- **重新标记**：修正并发标记阶段，用户线程持续运行导致的对象引用关系变化，**STW** 保证正确性。
- **并发清除**：清理垃圾对象，因为标记-清除算法不需要移动存活对象，所以此阶段 GC 与用户线程可以同时执行。

2. 缺点

- 内存碎片较多，在分配大对象时，更容易触发`Concurrent Mode Failure`和 Full GC。
- CMS 是并行回收，会占用 CPU 资源，导致用户线程吞吐量变低。
- CMS 无法处理**浮动垃圾**。如果并发清除阶段产生新的垃圾，CMS 无法对这些垃圾对象进行标记，只能在下次 GC 时回收。

### 2. G1

- 回收以区域为单位，YGC 采用**标记-复制**，整体上是**标记-整理**，避免了内存碎片问题。G1 会记录各个区域回收能获得的空间以及回收所需时间的经验值，维护一个**优先列表**，根据时间限制优先回收价值最大的区域。
- G1 注重**可预测的停顿时间**兼顾**吞吐量和延迟**，从 JDK9 开始为默认 GC。适用于大内存、多处理器的服务端应用。

1. **区域 Region**

- G1 将堆内存被划分为大小相同的独立区域，Region 大小为 2 的幂次，并且在整个 JVM 生命周期都不会改变。保留了逻辑上的年轻代、老年代，但不要求内存是连续的。
- Region 在分配对象内存时采用**指针碰撞**（区域内内存连续）。G1 设置了`Humongous` 区域专门存储大小超过 0.5 个 Region 的**大对象**，如果一个 H 区不够，G1 会寻找连续的 H 区，如果没有就会启动 Full GC。大对象在逻辑上被看作老年代对象。
- 如果 Region 被多个线程同时使用，可以用类似 TLAB 的方式为线程分配独立内存。

2. **Remember Set**

- 一个对象可能被不同区域引用，为了避免**全堆扫描**，G1 为每个区域维护一个`Remember Set` 记录哪些区域中有对象引用本区域的对象。
- 每次对引用变量进行写操作时，产生写屏障中断操作。检查引用对象和被引用对象是否在同一区域，如果不同，则将引用信息写入 Remember Set。
- 发生 GC 时，**Remember Set 会被加入 GC Roots**。

3. **Young GC**

- 当 Eden 区内存不足时，使用**标记-复制**算法进行 Young GC。将 Eden 区、S0 区中存活对象复制到空白的区域中即 S1 区。
- YGC 会附带一次**初始标记（STW）**：标记 **GC Roots** 的直接引用对象。**YGC** 时会触发一次初始标记。

4. **混合回收****（并发标记 + YGC）**

- 当老年代内存达到阈值`-XX:InitiatingHeapOccupancyPercent` (默认 **45%**)，开始混合回收。
- **原始快照 SATB**：在初始标记之后，并发标记之前，使用快照记录
- **并发标记**：在整个堆中并发扫描**可达对象**，计算每个区域的**存活对象比例**。此过程可以被 YGC 打断。
- **重新标记（STW）**：使用**原始快照**记录灰色对象引用的白色对象，然后以白色对象为根再次扫描，白色对象会被标记为灰色对象。避免漏标，但是可能多标。
- **筛选回收（STW）**：按垃圾比例对区域进行排序，如果整个区域对象全是垃圾，该区域可以被立即回收。
- 混合回收

- 老年代区域默认分 8 次（`-XX:G1MixedGCCountTarget`）完成回收。
- 每次混合回收，会将垃圾比例最高且垃圾比例达到阈值(`-XX:G1MixedGCLiveThresholdPercent` 默认 65%) 的区域加入回收集，然后用 YGC 回收年轻代和部分老年代。
- 当堆内存垃圾占比低于阈值 (`-XX:G1HeapWastePercent` 默认10%)或者达到时间阈值，即使混合回收没有达到 8 次，也不会再继续。

5. **Full GC**

- YGC 或混合回收时，如果存活对象晋升到老年代，但是老年代内存不足时。
- 在并发标记过程中，内存就耗尽了。

### 3. ZGC

与 ParNew 和 G1 类似，ZGC 也采用标记-复制算法，不过 ZGC 对该算法做了重大改进。ZGC 可以将暂停时间控制在几毫秒以内，且暂停时间不受堆内存大小的影响，出现 Stop The World 的情况会更少，但代价是牺牲了一些吞吐量。ZGC 最大支持 16TB 的堆内存。
