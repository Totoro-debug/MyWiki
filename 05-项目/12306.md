# 一、组件库

## (一) 基础组件

1. 封装 Spring 应用上下文

- `ApplicationContextHolder` 持有 ApplicationContext 对象，就能实现在非 Spring Bean 中使用 IOC 容器中的 Bean。

2. FastJson2 的安全模式

- Fastjson 的 "autoType" 特性是指在反序列化过程中，允许将 JSON 字符串自动转换为指定的 Java 类型，而无需手动指定目标类。攻击者可以构造恶意的 JSON 数据，其中包含对不受信任的类的引用。当 "autoType" 特性被启用时，Fastjson 会尝试根据 JSON 字符串中的类信息实例化相应的对象，从而可能导致潜在的安全问题。
- 开启 Fastjson 的安全模式，可以关闭 autoType 特性。

3. 单例对象容器

- 单例容器存储一些全局唯一的单例对象。

## (二) 规约组件

1. 定义异常码接口，定义基础异常码枚举类存储一级、二级异常码。

- 一级异常包括客户端异常、服务器异常、三方调用异常。

2. 定义抽象异常类以及客户端、服务端、三方调用抽象异常类。
3. 定义公共响应对象及其工具类。

## (三) 用户上下文组件

1. 定义 JWT 工具类，通过 JWT 将用户信息（userid、username）转换为唯一 token，并提供反解析 Token 方法。
2. 定义用户信息实体，并使用 ThreadLocal 存储用户上下文。
3. 定义用户上下文过滤器`UserTransmitFilter`，如果 http 请求头中同时包含 userId 和 userName，则尝试获取用户 token，并创建对应的用户信息实体放进用户上下文中。请求结束后，再移除用户信息实体防止 ThreadLocal 发生内存泄露。

## (四) 数据库组件

1. 定义基础实体`BaseDO`，包含公共字段如：创建时间、更新时间、删除标志。
2. 定义通用元数据处理器，当向数据库中插入或更新数据时自动填充某些字段。
3. 创建 MybatisPlus 的 MySQL 分页插件配置，避免重复配置。
4. 使用自定义雪花算法替换 MybatisPlus 原有的雪花算法 ID 生成器。

## (五) 自定义分布式 ID 组件 —— 雪花算法

- SnowFlakeID 是一个 64 位的 long 型整数，包含：

- 符号位：1bit，不使用。
- 时间戳：41bit，单位为毫秒，最长可以使用 69 年。
- 机器号：10bit，最多支持 1024 个节点部署。
- 序列号：12bit，最多支持 1ms 内生成 4096 个 ID。

- 优点：高性能高可用、ID 自增对 MySQL 索引友好。
- 缺点：如果服务器发生时钟回拨，可能导致 ID 冲突。
- **机器号获取**

- 默认使用 redis 存储`dataCenterId`、`workId`，使用 lua 脚本获取和更新机器码配置。
- 使用随机生成作为项目获取机器号的备用途径。

## (七) 幂等组件

### 1. 幂等方法

- 分布式锁：用户提交请求时，用一个唯一标识获取分布式锁，避免重复消费。
- Token 令牌：客户端在正式调用业务请求前，需要先从服务器获取一个全局唯一 Token。然后客户端在执行业务请求时要携带这个 token，服务器则要验证 token 的合法性，如果 Redis 中不存在该 token 则说明消息已经消费。
- 去重表：用 Redis 或者 MySQL 等存储已经处理过的请求，服务器在处理请求前要验证该请求是否已经被处理。如果已经存在记录说明请求已经处理过，否则进行消费。

### 2. 幂等注解

1. 幂等注解

- scene 字段表示幂等场景：RESTAPI、MQ，type 字段表示验证幂等方法：PARAM、SPEL。

2. Spring AOP

- 用`@Aspect`注解修饰幂等处理切面类。
- 用`@Around`标记具体幂等逻辑处理方法。

3. 消息幂等逻辑

- 用 lua 脚本执行 set nx get 的命令，如果 redis 中没有该 key，则说明未消费，反之说明消费过或者正在消费。
- 如果没有消费过，则执行业务逻辑，如果执行成功则将幂等标记值改为已消费；如果执行失败，则删除幂等标记，等待后续消费。
- 如果相同的消息正在消费，则返回 null 表示消费成功。如果相同消息已经消费过了，则抛出异常。

## (八) 设计模式

### 1. 责任链模式

- 责任链模式分为两种：一种是无论什么情况，请求都会被所有处理器处理一遍；另一种是如果请求不满足责任链中任一处理器定义的规则，都要停止流程，并抛出异常。

1. 好处

- 降低代码复杂度，增强灵活性和扩展性。
- 满足开闭原则，添加新的功能时，不需要修改已有代码。

2. 责任链过长可能会对系统性能造成影响。
3. 实现

- 责任链处理器接口继承自 `Ordered`接口，用来支持责任链按照优先级排序，实现顺序处理。handler() 抽象方法是具体执行逻辑，mark() 抽象方法是该处理器所属责任链的标识。
- 创建责任链上下文容器`Map<String, List<AbstractChainHandler>>`，key 为责任链标识，value 为责任链中所有处理器构成的链表。
- 通过`getBeansOfType`方法从 Spring 的应用上下文中获取处理器接口的所有实现类 Bean，然后根据责任链标记将不同的责任链处理器分类组装成 list 并放进责任链容器中。
- 责任链使用者调用执行方法，获取该责任链所有处理器，并根据定义的执行顺序依次执行。

### 2. 策略模式的实现

- 定义抽象执行策略接口，mark() 方法为策略标识。
- 创建策略选择器，使用`Map<String, AbstractExecuteStrategy>`保存策略标识及其具体的策略实现。

# 二、项目实现

## (一) 用户模块

### 1. 数据库表

- t_user：username 分片，唯一索引（username）
- t_user_mail：mail 分片，唯一索引（mail）
- t_user_phone：phone 分片，唯一索引（phone）
- t_passenger：username 分片，唯一索引（phone，id_type，id_card）
- t_user_deletion：不分片，唯一索引（id_type, id_card），记录同一个身份证件注销次数。
- t_user_reuse：不分片，唯一索引（username），记录哪些用户名注销过，则可以复用。

### 2. 责任链

- 用户注册责任链：检查用户注册参数、用户名与手机号等的格式、用户身份注销次数等。
- 乘客添加责任链：检查添加乘客的参数。
- 乘客删除责任链：检查删除乘客信息是否真实存在，然后检查乘客是否为当前用户本人。

### 3. 用户注册、登录的缓存穿透问题

- 使用布隆过滤器存储已注册用户名，注册和登录时都要检查是否存在该用户名。
- 登陆时，如果显示存在。再去 redis 缓存中检查是否是已注销用户名，如果注销过则可以复用。

### 4. 敏感信息加密

- 使用 ShardingShpere 对敏感数据进行加密，数据库存储的是密文数据，使用 AES 算法（对称加密）。

## (二) 查票

### 1. 数据库表

- t_train：主键 id
- t_carriage：唯一索引（train_id, carriage_number）
- t_seat：普通索引（train_id, start_station, end_station, seat_type）某列火车从某一站到某一站的某一种作为不可能只有一个。
- t_region：唯一索引（code）、（name）
- t_station：唯一索引（code）、（name）
- **t_train_station_relation**：唯一索引（start_region, end_region, train_id）。**列车站点关系表**维护了某列火车的所有站点的区间配对，每辆列车由 Cn2 条记录。
- **t_train_station_price**：唯一索引（train_id, departure, arrival, seat_type）。**列车站点价格表**维护了某列火车的所有站点的区间配对与座位类型组合记录。
- **t_train_stop_station**：唯一索引（train_id, sequence）。列车停靠站表维护了某列火车的所有停靠站、该站的停靠时间、该找到下一站的理论时间。

### 2. 责任链

- 列车查询责任链：检查列车参数非空、日期、出发站和目的站不能相同、是否真实存在。

### 3. 查票流程

1. 用户输入**出发站**、**目的站**、**出发日期**，先走责任链做参数校验。
2. 将站点映射成**城市**，两个原因：① 地区组合比站点组合少，可以降低缓存 key 数量；② 用户指定的站点不一定有车次，但是粒度扩大到城市，可选的车次就变多了。
3. 用 `**出发日期_出发城市_目的城市**` key 查询 redis，得到列车在该区间基本信息的列表。

- 如果缓存未命中，查询**列车站点关系表**中，所有出发城市、目的城市等于映射后的城市名，并且出发时间在用户选定日期内的记录。
- 然后查询列车表得到一些基本信息，构建前端展示所需要的实体列表。

4. 补齐票价信息：用 `**列车id_出发站点_目的站点**` key 查询缓存，得到价格信息列表。

- 如果缓存未命中，查**列车站点价格表**得到列车的价格信息。

5. 补齐余票信息：查询余票缓存，如果缓存未命中，查询座位表。
6. 将结果汇总后返回给前端。

### 4. 查票防止缓存击穿

- 如果用户输入的条件，缓存未命中。通过 Redisson 的分布式锁 + 双重检查锁，保证同一时刻只有一个线程在重建缓存，避免大量请求同时打到数据库。

### 5. 查票为什么使用 Pipeline

- 列车的基本信息、价格信息、余票信息，可能都涉及到很多个列车，如果一个一个查会产生大量的网络 IO，使用 Pipeline 可以一次网络 IO 查询多个列车。这样讲多个 RTT 压缩成一个 RTT，提升接口响应速度。

### 6. 热点 key（热门城市、节假日）

- 根据历史经验，提前将热点数据加载到缓存中。
- 可以利用一个有效期较短的本地缓存，做热点削峰，减轻 redis 的压力。

## (三) 购票

### 1. 责任链

- 购票责任链：检查参数合法、乘客信息合法、列车余票是否充足。

### 2. 购票主流程

1. 用户在前端选择**列车**、**区间**、**乘客**、**座位类型**，走责任链检查：参数、乘车人信息、余票。
2. 使用 Lua 脚本对令牌桶中所有收到影响的区间的令牌进行预扣减，如果没有充足令牌，则返回拒绝信息。然后触发一个延迟任务，这个延迟任务不会重建缓存，而是删除令牌桶，让后续请求重建令牌桶。
3. 拿到令牌后，以 `trainId + seatType` 为 key 即以作为类型为锁粒度，按序获取本地锁和分布式锁。
4. 为用户分配座位，得到具体的**车厢号和座位号**。
5. 然后批量修改所有受到影响的座位的状态 `available -> locked`。
6. 然后调用订单服务，创建订单，返回订单号。
7. 释放分布式锁和本地锁。

### 3. 为什么要做幂等

- 防止因为网络或重复点击，导致用户一次请求，创建了多个订单。

### 4. 如何防超卖

1. Redis 令牌桶：快速失败，阻拦无效流量。
2. 锁：通过本地锁+分布式锁，同一作为类型只能串行化操作，降低并发风险。
3. 座位分配：锁定座位状态。

### 5. 选座算法

- 首先按照座位类型分组，如果有多个组，通过线程池**并行**处理。
- 同一个座位类型内，如果需要购买多张票，优先找相邻座位，没有则找同车厢座位，最后降级为找到就行。

### 6. 购票和订单怎么保持一致性

- **选座算法**和**座位加锁**都是在本地事务中的，如果这些操作失败，就直接回滚不涉及订单。
- 调用订单远程服务，同样是在本地事务中的，如果订单创建失败，同样会导致本地事务回滚。
- 订单延迟关闭、订单主动取消，是通过 canal 监听 Mysql 的座位表和订单表。

## (四) 订单

- 首先生成全局唯一订单号，然后拼接用户 id 后六位，得到与用户 id 有关的全局唯一订单号。
- 创建订单、订单明细、订单乘客关联信息并插入数据库。

- 订单表/订单明细表：分片算法根据用户 id、orderSn 后六位分表。
- 订单乘客关联表：对乘客证件号哈希取模。

- 为用户创建订单，创建成功后，给 RokcetMq 发送延迟消息，订单服务中有消费者对订单延迟关闭进行消费。

### 1. 订单延迟关闭

- order-service 创建订单完成后发送延迟消息，消息到期后，由 ticket-service 中的消费者消费这条消息。
- 首先调用 order 服务的接口关闭订单，主要是确定订单是否存在、修改订单状态。
- 如果没有启用 canal，则由当前消费者修改座位状态并回滚余票缓存和令牌。
- 如果启用了 canal，则由订阅 canal 消息的消费者修改座位状态并回滚余票缓存和令牌。

## (五) 支付回调

- 订单服务中支付回调消费者主要处理订单和明细的状态。
- 购票服务中支付回调消费者主要处理座位的状态

## (六) 远程调用 - OpenFeign

- 使用 OpenFeign 实现一个服务调用另一个服务接口，底层也是通过动态代理，扫描@OpenFeign 注解的接口，然后生成代理类，从@GetMapping等注释中获得请求路径，在和 url 属性拼接得到完成 url。
- 通过 OpenFeign 调用其他服务接口相当于，发送 http 请求并接受 http 响应。

# 三、 Q & A

## (一) 自定义组件库

- SpringBoot Starter 类似于一种插件机制，遵循“约定大于配置”理念。将复杂的依赖集成进 Starter，开发者只需要引入 Starter 依赖，SpringBoot 可以自动加载所需要依赖。
- core + 自动配置类 + pom + 自动装配文件（META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports）。

## (二) 列车数据搜索？为什么使用 Redis 不使用 ES？

- 首先，12306 的列车搜索的条件并不复杂：只有出发地、目的地、出发日期，筛选操作可以在前端完成，只是起到一个展示的作用，并不需要每次更改条件都重新查询。这意味着可以很容易的利用查询条件作为 key 构建列车数据缓存，对于热门车次，只需要一次查询就可以多次使用。
- 其次，在项目中，列车查询功能主要与 t_train_station_relation、t_train_station_price、t_train、t_seat、t_train_stop_station 共 5 张表有关。因为列车搜索条件实际上也是查询数据库的筛选条件。所以，只要在这些表上建立合适的索引，就能提升数据库的查询速度。
- 整体来说，没有必要额外引入 ES 组件。

## (三) 订单延迟关闭有没有其他实现方案？

- 梯度

1. 定时任务

- 使用 xxl-job 等定时任务调度框架可以实现，但是此类框架一般都是使用类似轮询的方式扫描定时任务。在高并发场景下，可能导致大量定时任务被同时扫描到同时执行，导致系统压力过大。

2. Redis 过期监听

- 使用 Redis 的 PSUBSCRIBE 命令订阅过期事件，监听到过期事件后触发处理逻辑。

3. RabbitMQ

- RabbitMQ 也支持延迟消息功能，也可以实现类似功能。
- 首先，在生产环境中，RabbitMQ 可用性方面不如 RocketMQ，存在单点故障的问题，而 RocketMQ 搭建集群较为方便可以解决这个问题。
- 其次，因为项目中已经引入 RocketMQ，而 RocketMQ 的延迟消息使用起来比较简单。并且在 5.0 之后，RocketMQ 延迟消息的级别支持自定义时间了。

## (四) 缓存一致性

- 缓存双删
- 先更新数据库，再删除缓存
- 先更新数据库，Binlog 异步更新缓存

### 1. 介绍一下 Canal

- Canal 将自己伪装为 Mysql 的从节点，并向 Mysql 发送 dump 请求，Mysql 会向 Canal 推送 binlog 的增量更新。然后 Canal 解析 binlog 后，向下游的 RocketMQ、Kafka 等推送数据。
- Mysql 的 binlog 日志格式必须设置为 row。

### 2. 项目中使用的缓存一致性方案

- 使用 Canal 监听座位表和订单表的 binlog，然后发送消息到 RocketMQ，消费者消费这些消息并更新缓存一致性，实现最终一致性。

## (五) 如何解决高并发购票和防超卖问题？

- 采用了令牌桶限流思想。在 Redis 中缓存列车上不同席别的令牌，令牌数和余票数是一一对应的。只有通过 lua 脚本申请到令牌的用户才能购买，其余用户会直接返回提示信息。
- 拿到令牌的用户，需要分别申请分布式锁和本地锁，对用户购买的该列车的所需座位类型加锁。加锁成功后，才会正式给用户分配实际座位，并修改座位状态。

## (六) 用户注册防止缓存穿透

### 1. 常见方案

- 布隆过滤器
- Set 集合

### 2. 项目使用的方案

## (七) 自定义幂等注解

### 1. 自定义注解原理

- Spring AOP 主要通过动态代理，实现切面逻辑增强。
- Spring 会为被注解标记的方法所在的类创建代理对象，然后执行@Around 方法定义的逻辑。
