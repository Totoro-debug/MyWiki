# 一、分布式
- 分布式系统就是把**多台独立的计算机**通过**网络**连接起来，让它们**协同**工作，一起去完成同一个任务。但是对用户来说，访问分布式系统就像是访问**一个完整的系统**。
## (一) 为什么要用分布式系统
1. **高性能和高并发**
	- 单机的资源和性能是有限的，当系统流量逐渐增大后，必须将压力分散到多台机器上。
2. **高可用**
	- 单机存在**单点故障**问题，机器宕机整个系统就不可用了。但是在分布式系统中，部分机器宕机依然能够提供服务。

## (二) 分布式和微服务
|      | 分布式                                    | 微服务                                                   |
| :--: | :------------------------------------- | :---------------------------------------------------- |
|  本质  | 分布式是一种**机器部署**方式，将系统部署在多台机器上，解决单机的局限性。 | 微服务是**架构设计**思想，按业务拆分模块，提升可维护性、降低耦合度，不同服务可以独立开发、部署和扩展。 |
| 二者关系 | 分布式系统中服务可以是微服务，也可以是单体服务。               | 微服务可以单机部署，也可以分布式部署。                                   |
|  目标  | 提高系统的性能、容错能力、可扩展性                      | 提高系统可维护性、可扩展性、团队开发效率                                  |
| 典型场景 | 分布式缓存、分布式数据库、分布式文件系统                   | 电商系统拆分为用户服务、订单服务、支付服务等                                |

## (三) CAP 定理
- CAP 定理：在分布式系统中，一致性（C）、可用性（A）、分区容错性（P）三者不能同时满足。
1. **一致性 Consistency**：分布式系统的所有节点，同一时刻，看到的数据必须一致。
	- **强一致性**：所有读操作都返回最新的写操作结果。
		- 线性一致性：强调实时性，任何时间读操作都应该返回最新的写操作结果。
		- 顺序一致性：系统维护一个全局操作顺序，保证每个客户端看到的操作顺序都一致。
	- **弱一致性**：允许一定程度的不一致，换取高性能和可用性。
	- **最终一致性**：一段时间内可能数据不一致，但是最终达到一致状态。
2. **可用性 Availability**：用户访问系统，系统必须总能响应用户的读/写请求。
3. **分区容错性 Partition tolerance**：节点之间出现通信故障时，系统也要能持续提供服务。
	- 分区容错性是分布式系统的**基本要求**，因为通信故障无法彻底避免，只能在一致性和可用性之间做取舍。
4. **CP 和 AP**
	- CP：如果出现网络故障，用户不能写，只能读，直到网络恢复。
	- AP：如果出现网络故障，允许用户任意读写，但是这样就会导致数据不一致。
	- MySQL
		- 主从结构 Mysql 同一时刻只有主库提供服务，是 AC 系统。
		- 读写分离 Mysql 中主库写，从库读，是 Ap 系统。
	- Zookeeper (CP)：ZAB 算法实现了**顺序一致性**，保证每个节点上读取到的一定是最后一次更新的内容。
5. **PACELC** 理论
	- 如果存在分区（P），必须在可用性（A）和一致性（C）之间选择；否则（E，Else），必须在延迟（L）和一致性（C）之间选择。

## (四) BASE 理论
- BASE 指 **Basically Available（基本可用）**、**Soft-state（软状态）** 和 **Eventually Consistent（最终一致性）**，它是 ACID 在分布式场景下的替代。
1. **基本可用**：分布式系统在出现故障时，允许损失部分可⽤性 (例如：允许响应时间变长)，但是保证核⼼可⽤。
2. **软状态**：允许系统存在中间状态，且中间状态并不影响系统整体可⽤性。而 ACID 要求事务结束必须进入终态。
3. **最终⼀致性**：虽然⽆法保证强⼀致性，但是在软状态结束后，最终达到数据⼀致（要么成功，要么回滚）。

# 二、分布式 ID
- 分布式 ID 指分布式系统中用于跨节点、跨库、跨服务唯一标识数据的 ID。
## (一) 基于数据库
### 1.1 数据库主键
- 数据库全局自增的性能太差。
### 1.2 Redis 自增
- Redis 全局自增的性能优异。但是存在：持久化延迟或主从切换导致 ID 回退、热点 Key 等问题。
### 1.3 号段模式
- 从数据库中批量获取一个 **ID区间 (号段)**，缓存在本地内存中，分配 id 时直接从本地获取，直到 id 分配完毕再获取下一个号段。
- 用一个专门的表记录**号段分配进度**，典型结构为：**① 业务 id、② 已分配最大 id、③ 号段大小**。
- 优化：在号段即将耗尽之前，**提前申请下一个号段**，等当前号段使用完毕后无需等待直接使用。

## (二) 基于分布式 ID 算法
### 2.1 雪花算法 (Twitter 提出)
- SnowFlakeID 是一个 64 位的 long 型整数，包含：
	- 符号位：1bit，不使用。
	- 时间戳：41bit，单位为毫秒，最长可以使用 69 年。
	- 机器号：10bit，最多支持 1024 个节点部署。
	- 序列号：12bit，最多支持 1ms 内生成 4096 个 ID。
- 优点：高性能高可用、ID 自增对 MySQL 索引友好。
- 缺点：如果服务器发生时钟回拨，可能导致 ID 冲突。
1. 时钟回拨问题
	1. 拒绝服务。
	2. 等待服务器时间追回上次记录的时间。
	3. 使用备用 workerId，可能存在脑裂问题，需要保证全局唯一。
2. WorkerID 分配问题
	1. 使用 Zookeeper，服务启动时在 ZK 中创建一个**临时节点**，节点序号作为全局唯一 WorkerID。
	2. 使用 Redis 记录 WorkerID。
### 2.2 UUID
- Java 的 `UUID.randomUUID()` 生成的是 v4 版本，基于伪随机数生成，理论上存在重复的可能。
- UUID v7 基于**时间戳**生成，高 48 位为 Unix 毫秒级时间戳，剩余位中包含版本、变体标识、随机数。

## (三) 成熟分布式 ID 组件
### 3.1 美团 Leaf
1. 号段模式：支持双号段，当号段消耗到一定阈值后，由异步线程提前去数据库申请下一个号段。
2. 雪花算法：依赖 ZooKeeper 作为注册中心管理 WorkerID。
### 3.2 滴滴 TinyID
- 基于号段模式生成唯一 ID。主要优化包括：
	- 双号段缓存。
	- 多数据库支持。
	- 通过 client 代理，性能和可用性大大提高。

# 三、分布式锁
## (一) 数据库
- 用数据库的**唯一索引**实现同一时间只有一个线程能加锁，插入成功 = 加锁，删除 = 释放锁。

## (二) Redis 的 set nx 命令
- 利用 set nx 和 redis 的原子性实现分布式锁，性能高。
- 释放锁时通过 Lua 脚本比较唯一的 value 防止误删锁。
- 缺点：无法实现重入，锁续期不方便。

## (三) Redisson 的 RedissonLock
1. 利用 Redis 的 Hash 结构实现
	- **key**：就是自定义锁名称。
	- **field**：Redisson 实例的 Id 拼接线程 id 即 `UUID: threadId`，实现全局唯一指定线程。
	- **value**：该线程的重入次数。
2. 通过 **Lua 脚本实现加锁和重入**
```lua
-- 如果锁不存在、或存在并且持有者是当前线程
if ((redis.call('exists', KEYS[1]) == 0) or (redis.call('hexists', KEYS[1], ARGV[2]) == 1)) then 
  redis.call('hincrby', KEYS[1], ARGV[2], 1);	-- 重入次数自增 (不存在设为 1，存在加 1)
  redis.call('pexpire', KEYS[1], ARGV[1]); 		-- 设置 key 的有效期
  return nil; 									-- 加锁成功返回 null
end; 

return redis.call('pttl', KEYS[1]);  		 	-- 加锁失败返回锁的剩余过期时间
```
3. **看门狗机制**
	- 当没有指定锁超时时间时，默认过期时间为 30s。在 `renewExpiration()` 方法中，会启动一个 Redisson 的定时任务，这个定时任务每隔 1/3 过期时间即 10s 就通过 Lua 脚本刷新锁的过期时间。
	- 如果看门狗没有在 **finally** 中手动释放，那么如果发生异常导致线程提前返回但是又没有释放锁，那么该锁会被看门狗一直续期直到 JVM 停止。

## (四) ZooKeeper
- ZooKeeper 分布式锁是基于**临时顺序节点**和 Watcher (事件监听器) 实现的。
- 每个数据节点在 ZooKeeper 中被称为 znode，它是 ZooKeeper 中数据的最小单元。我们通常是将 znode 分为 4 大类：
	- **持久 (PERSISTENT)** 节点：一旦创建就一直存在即使 ZooKeeper 集群宕机，直到将其删除。
	- **临时 (EPHEMERAL)** 节点：临时节点的生命周期是与 客户端会话 (session) 绑定的，会话消失则节点消失 。并且，临时节点只能做叶子节点 ，不能创建子节点。
	- **持久顺序 (PERSISTENT_SEQUENTIAL)** 节点：除了具有持久 (PERSISTENT) 节点的特性之外， 子节点的名称还具有顺序性。比如 /node1/app0000000001、/node1/app0000000002 。
	- **临时顺序 (EPHEMERAL_SEQUENTIAL)** 节点：除了具备临时 (EPHEMERAL) 节点的特性之外，子节点的名称还具有顺序性。
- **Watcher (事件监听器)** ，是 ZooKeeper 中的一个很重要的特性。ZooKeeper 允许用户在指定节点上注册一些 Watcher，并且在一些特定事件触发的时候，ZooKeeper 服务端会将事件通知到感兴趣的客户端上去，该机制是 ZooKeeper 实现分布式协调服务的重要特性。
- 基于 ZK 的分布式锁中的事件监听器的作用是：当前一个节点对应的客户端释放锁之后 (也就是前一个节点被删除之后，监听的是**删除事件**) ，通知获取锁失败的客户端 (唤醒等待的线程，Java 中的 wait/notifyAll ) ，让它尝试去获取锁，然后就成功获取锁了。
# 四、分布式事务
- 简单来说，业务代码涉及到跨多台服务器或多个微服务，就必须保证**跨节点**的操作：要么全部成功，要么全部失败。
## (一) AT 模式 (Automatic Transaction)
- 核心目标是尽量少的改动业务代码，提供最终一致性。简单理解就是“自动补偿”：业务仍然执行本地事务，但是框架会记录回滚需要的信息。
1. AT 过程
	- 一阶段：业务正常执行 SQL 并**提交本地事务**。AT 框架负责解析 SQL 并**记录原始快照**，然后向协调者注册该本地事务。
	- 二阶段：如果全局事务提交，协调者通知参与者**删除快照**。如果全局事务回滚，参与者**根据快照回滚**。
2. 优点：代码侵入性低，适配绝大多数关系型数据库的 CRUD 场景。
3. 缺点：① 对 SQL、表、隔离级别等有限制。② 不适合复杂 SQL 和非关系型数据库场景。

## (二) XA 模式
- **AP (Application Program)**：应用程序，负责**发起**分布式事务。
- **RM (Resource Manager)**：资源管理器也称**参与者**，绝大部分情况下就是指数据库。
- **TM (Transaction Manager)**：事务管理器也称**协调者**，负责管理分布式事务，分配事务唯一标识，监控事务的执行进度，并负责事务的提交、回滚、失败恢复等。

### 1. 二阶段提交 2PC (强一致性)
1. 2PC 过程
	1. **准备阶段 Prepare**
		- 协调者向参与者发送**事务准备执行的消息**，等待参与者回复。
		- 参与者收到消息后，**执行本地事务但不提交**，然后向协调者反馈是否成功的结果。
	2. **提交阶段 Commit**
		- 协调者**检测所有参与者本地事务执行状态**：如果都成功，通知所有参与者提交事务；否则，全部回滚。
		- 参与者接受协调者命令，**提交或回滚事务并释放资源**，然后向协调者回复 ACK 消息。
2. 优点
	- 模型简单，容易实现。主流数据库都支持 XA 事务，可以作为 2PC 中的 RM/参与者。
	- 能够实现强一致性。
3. 缺点
	- **同步阻塞**：参与者在提交事务之前会一直占用资源，其他节点访问该资源就会阻塞。
	- **单点故障**：协调者如果在 Prepare 完成后 Commit 开始前发生故障，参与者就会一直阻塞。
	- **数据不一致**：由于网络问题或者协调者宕机都有可能会造成数据不一致的情况。例如：部分参与者收不到 Commit/Rollback 消息。

### 2. 三阶段提交 3PC (强一致性)
- 在 2PC 基础上，将准备阶段拆分为询问、预执行两个阶段，最后再提交。
1. 3PC 过程
	1. **询问阶段 CanCommit**：询问所有参与者是否可以执行事务，参与者不执行本地事务，返回 Yes、No或超时。
	2. **准备阶段 PreCommit**：如果所有参与者全都回复 Yes，通知所有参与者**执行事务**；否则，发送 Abort 通知参与者**中断事务**。参与者执行完本地事务后，根据结果返回 Yes、No或超时。
	3. **提交阶段 DoCommit**：如果所有参与者全都回复 Yes，通知所有参与者提交事务；否则，全部回滚。
2. 与2PC相比
	- 引入超时机制，避免长时间阻塞。
	- 性能更差，且数据还是会不一致。

## (三) TCC (**最终一致性**)
1. 将事务分为 try、confirm、cancel 三个操作。
	- **Try**：参与者尝试执行本地事务，并为**全局事务预留资源**，最后返回事务执行结果。
	- **Confirm**：如果所有参与者 try 都执行成功，Confirm 阶段**使用 Try 预留的资源完成事务**，最后提交事务并释放资源。
	- **Cancel**：如果有参与者 try 失败，所有参与者都要**回滚并释放**预留的资源。
2. 问题
	- **空回滚**：try 阶段部分参与者可能因为网络等问题没有执行 try 操作，但是 cancel 阶段执行不正确的回滚和释放不存在的资源。解决：参与者接收到 cancel 先查询是否有 try 记录，没有可以直接返回成功。
	- **悬挂**：因为网络阻塞等问题，try 操作比 cancel 更迟到达，导致先 cancel 后 try，占用的资源可能永远不会被  confirm 或 cancel。解决：参与者收到 try 先查询是否该事务是否被 cancel 过，如果是则拒绝 try。
	- **幂等性**：Confirm 和 Cancel 可能因为网络超时、TC 重试等原因被重复调用，必须保证多次执行结果一致。解决：数据库中引入分布式事务表记录分布式事务操作。
3. 优点：不会一直持有资源的锁，避免长时间等待。性能相对更好。
4. 缺点：TCC 需要修改业务代码，**代码侵入性**和**耦合性**相对较强。追求最终一致性，而不是强一致性。
## (四) Seata 框架
- 阿里开源的一站式分布式事务解决方案，核心角色包括：
	- **TC（Transaction Coordinator）**：事务协调者，维护全局事务和分支事务状态。
	- **TM（Transaction Manager）**：事务管理器，定义全局事务边界，负责开启、提交或回滚全局事务。
	- **RM（Resource Manager）**：资源管理器，管理分支事务资源，向 TC 注册分支事务并上报状态。
- Seata 支持 AT、XA、TCC、Saga 事务。

# 五、分布式一致性算法
## (一) Raft 算法
### 1. 节点类型
- 一个 Raft 集群中，有且只有三种角色。
- **Leader (领导者)**：只有一个。负责接待客户端、写账本、同步账本给 Follower。Leader 必须不断地向全员发送心跳，声明自己的存活状态。
- **Follower (跟随者)**：不主动发起请求，只被动接收 Leader 的心跳和账本同步。
- **Candidate (候选人)**：一种临时状态。Follower 一定时间没收到 Leader 的心跳，就会将状态变更为候选人开始拉票。
### 2. 任期机制
- Raft 算法会给任期编号即 **term 号**，所有节点都必须存储当前 term 号。节点之间通信时会交换 term 号，如果发现 term 号比对方小，则更新 term 号。
- 如果 Leader 或 Candidate 发现自己的 term 号过期了，就会立即**降级为 Follower**，然后导致选举的发起。

![[Raft 任期.png]]
### 3. 选举
- Follower 在选举计时器超时前每收到 Leader 的心跳，就会开始一次选举。
- Follower 会自增 term 号，并将自己的状态转换为 Candidate，然后向所有节点发起投票请求
	- 如果有更高的 term 号，立即退回 Follower。
	- 如果收到其他 term 号不低于自己的 Leader 心跳，立即退回 Follower。
	- 如果超时/分票，则发起下一轮投票（term++ 重复以上流程）。
	- 如果收到 (N/2 + 1) 个投票，就成为新的 Leader。
### 4. 日志复制
- 客户端的请求发给 Leader 后，会生成一条 <index,term,cmd> 日志，然后将该日志追加到日志末尾。
- Leader 向所有 Follower 广播该日志，Follower 将该日志追加到自己本地日志后返回确认。等到超过一半 Follower 返回确认后，Leader 才会将该日志提交并通知 Follower 提交。
- Follower 更新本地索引，并执行这些操作。

# 六、配置中心
- 配置中心主要解决的是服务**配置的集中管理**、**配置推送**、**环境隔离**、**灰度发布**、**审计日志**等问题。
## (一) 配置推送机制
- 长轮询本质上还是**客户端拉取**，只是服务器保持长连接并挂起客户端请求，当配置发生更新时再返回响应。

| 模式      | 实时性      | 服务端压力          | 实现复杂度 | 适用场景     |
| ------- | -------- | -------------- | ----- | -------- |
| **推模式** | 高（毫秒级）   | 高（需维护连接）       | 高     | 强实时性要求   |
| **拉模式** | 低（秒~分钟级） | 高（无效轮询）        | 低     | 配置变更极少   |
| **长轮询** | 中高（秒级）   | 中等（海量连接时内存压力大） | 中     | **主流方案** |

## (二) 客户端容灾
1. **多级缓存**：配置中心不可用时，优先读取内存中缓存的快照；快照不存在时，优先使用代码中的兜底默认值。
2. **降级启动**：配置中心不可用，可以使用默认值。对于数据库地址、密钥等关键配置，无配置就拒绝启动。
3. **断线重连**：客户端连接断开后，使用退避策略 (如指数退避) 以免给服务器造成太大压力。

## (三) Apollo 配置中心
- **实时配置（热发布）**：基于长轮询，1s 内即可接收到最新配置
- **灰度发布**：配置只推给部分应用，降低变更风险
- **部署简单**：单环境仅依赖 MySQL；Apollo 自带的注册中心（默认为 Eureka）以内嵌方式运行于 Config Service 进程内，无需独立部署。多环境物理隔离时，需要为每个环境部署一套 Config Service、Admin Service 和独立数据库
- **跨语言**：提供了 HTTP 接口，不限制编程语言
### 1. Apollo 架构
| 组件                 | 作用                                                 | 默认端口                |
| ------------------ | -------------------------------------------------- | ------------------- |
| **Portal**         | Web UI 作为管理界面                                      | 8070                |
| **Admin Service**  | 向 Protal 提供配置管理接口，拥有将**配置写入 MySQL** 的能力。           | 8090                |
| **Client**         | 客户端 SDK，可以调用 Config Service 的接口**获取配置**和**监听变更**   | -                   |
| **Meta Server**    | 服务发现入口，与 Config Service 同进程，供 Client/Portal 获取服务地址 | 8080                |
| **Config Service** | 内嵌 Eureka 作为注册中心，向 Client 提供**配置获取**和**长轮询通知**的接口  | 8080                |
| **Eureka（内嵌）**     | 内嵌在 Config Service 中，供 Config/Admin Service 注册发现   | 与 Config Service 相同 |
| **MySQL**          | 存储配置数据和元数据                                         | 3306                |
### 2. Client 拉取配置
1. Client 启动时访问 Meta Server 获取 Config Service 地址列表。
2. Client 缓存服务地址，以防 Eureka 故障。
3. Client 通过长轮询获取配置，Config Service 检测到配置变更后立即响应。
4. Client 更新配置缓存，并将配置异步持久化到文件。
### 3. Portal 发布配置
1. 在 Portal 中更新并发布配置，Portal 会调用 Admin Service 的接口将配置写入 MySQL。
2. Config Service 通过 Client 发起的长轮询通知配置变更，Client 获取最新配置。


## (四) Nacos
- 由阿里开源，集 **服务注册与发现**、**配置中心** 与一体。
### 1. 命名空间
- Nacos 提供了基于命名空间的**环境隔离**功能，并且通过**三层模型唯一定位**一份配置。
1. `命名空间 Namespace`：用于环境隔离。默认为空，表示 public。
2. `分组 Group`：对服务或配置分组。默认为 DEFAULT_GROUP。
3. `服务名/配置名 ServiceId/DataId`：用于服务注册与发现时，表示服务名；用于配置管理时，表示配置文件标识。


### 2. 分级模型
- 在一个服务下，可以存在若干个集群 Cluster，一个集群中可以存在若干实例 Instance。

# 八、RPC

- RPC（Remote Procedure Call） 即远程过程调用，可以帮助调用远程服务器上某个服务的方法，使得调用远程方法就像调用本地方法一样简单。

## (一) RPC 调用过程
1. **客户端**：客户端以本地调用的方式调用远程服务。
2. **客户端代理**：客户端代理类将**类名、方法、参数**等打包为调用请求，然后进行**序列化**，最后通过**网络传输**给服务端。
3. **服务端代理**：服务端代理类接收到客户端请求后，先进行**反序列化**，然后根据类、方法、参数等**查找并调用**本地方法。
4. **服务端**：执行方法调用，然后将结果交给代理类。
5. **服务端代理**：将结果组装成响应，然后**序列化**后通过网络返回给客户端代理。
6. **客户端代理**：收到消息后**反序列化**得到响应，然后将响应交给客户端。

## (二) RPC 核心能力
1. **代理调用**
	- 对于客户端/服务端来说，就像调用/执行了本地方法。中间过程由客户端/服务端代理进行处理：序列化、网络传输、服务发现、负载均衡、超时重试等。
2. **序列化/反序列化**
	- 客户端代理将请求序列化为适合网络传输的格式，比如说：JSON、ProtoBuf (二进制格式)。
	- 然后服务端代理进行反序列化。
3. **服务发现**
	- 帮助客户端知道某一个服务运行在哪些物理机器上，没有服务发现、RPC 就无法发起调用。
4. **网络传输**
	- 基于 TCP，例如：Dubbo、Thrift 等。
	- 基于 HTTP，例如：新版本的 Dubbo、gRPC 使用 HTTP/2。
	- 基于 Netty，也就是说将网络通信托管给 Netty，底层通过 NIO 网络模型提供高性能的网络服务。
5. **负载均衡**
	- 轮询、随机、哈希
6. **超时与重试**
	- 设置超时时间，自动重试。

## (三) 常见的 RPC 框架

### 1. Dubbo
- Dubbo 提供了从**服务定义**、**服务发现**、**服务通信**、**服务治理**等全面设施，支持 Triple 协议（基于 HTTP/2 之上定义的下一代 RPC 通信协议）、应用级服务发现、Dubbo Mesh等特性。

### 2. gRPC
- gRPC 是 Google 开源的一个高性能、通用的开源 RPC 框架，主要面向移动应用开发。
- 基于 **HTTP/2** 协议标准进行设计（支持双向流、消息头压缩等功能，更加节省带宽）。
- 基于 **ProtoBuf** 序列化协议开发，进一步节省网络带宽。
	- ProtoBuf (Protocol Buffer) 是一种更加灵活、高效的数据格式，可用于通讯协议、数据存储等领域，基本支持所有主流编程语言且与平台无关。但是 ProtoBuf 定义接口和数据类型较为繁琐。

## (四) RPC 与 REST api 对比
1. 使用
	- RPC 操作的是方法，因此 RPC 客户端和服务端是紧耦合的。
	- REST api 操作的是资源，它是基于 HTTP 的语义对资源进行操作，很容易通过代理改变资源位置。相比较，REST api 更加灵活，RPC 使用够简单。
