# 一、消息队列

## (一) 为什么消息队列

### 1. 异步

- 同步通信导致业务流程太长，异步可以让核心流程变短。

### 2. 解耦

- 让两个需要通信的模块或功能解耦，后续对一个模块修改、扩展等不会影响另一个模块。

### 3. 削峰填谷

- 用户请求先发送到消息队列，消费者根据消费能力从队列拉取消息进行处理。
- 持久化存储，支持消息重试、事务。

## (二) 为什么选择 RocketMQ

1. 事务消息：RocketMQ 支持事务消息。
2. 顺序消息：可以通过路由算法将消息路由到同一个队列，然后再用同一个消费者线程顺序消费，失败重试。
3. 高吞吐量、低延迟、高可用性。

# 三、RocketMQ 架构

## (一) RocketMQ 架构

### 1. NameServer 名字服务器

- NameSever 和 Broker 保持长连接，负责维护 Broker、Topic 的动态注册与发现、路由信息的管理。
- Broker 在启动时向 NameServer 中注册自己的地址、端口、topic 等，每个 Broker 都要同时和所有 NameServer 实例保持长连接，定时向 NameServer 同步自己维护的 Topic 信息。
- Producer 和 NameServer 中一个节点建立长连接，定期从 NameServer 中获取 Topic 的路由信息。
- Consumer 和 NameServer 中一个节点建立长连接，定期从 NameServer 中获取 Topic 的路由信息。

### 2. Broker 代理服务器

- 负责存储和转发消息，支持多个 Broker 构成集群。一个 Broker 中有多个 Topic。

1. Topic

- 主题是消息的逻辑分类，每一条消息都必须设置 Topic，作为消息发送的目的地。生产者发送消息到特定的 Topic，Consmuer 从某个 Topic 中取消息。
- 每个消息可以选择性设置 tag 作为消息的第二级类型。

2. Queue

- 消息队列是 Topic 的具体实现。一个 Topic 可以有多个队列，队列中存储消息的索引，消息实体存储在 CommiLog 中。
- Broker 会根据消费者的 queue offset 找到对应消息，返回给消费者。

### 3. Producer

- 消息生产者，将消息发送给 Broker。

### 4. Consumer

- 消费者，RocketMQ 是通过消费者组体现订阅者。每一个消费者组消费 Topic 一条消息，不同消费者组之间消费进度互不影响。

## (二) CommitLog 与 ConsumeQueue

- 整个消息队列中的消息无论 Topic、无论类型全都要按顺序写入 **CommitLog**，因为是顺序 IO 所以速度极快。一个 CommitLog 文件最大 1G，写满创建新的文件。
- ConsumeQueue 是逻辑消费队列，存储消息在 CommitLog 中的物理位置，相当于一个索引文件。消费者拉取消息的时候，本质上就是通过 ConsumeQueue 找到日志中实际的消息。

## (三) 消费模式

1. **pull 模式**

- 消费者主动去消息队列拉取消息，消费者控制拉取的速度、数量，需要不断轮询，浪费资源。

2. **push 模式**

- 消息队列主动把消息推送给消费者，消费者只需要注册一个监听器，消息一到达就触发回调进行处理，响应速度快，但可能会出现消息堆积的情况。

## (四) 消费方式

1. **集群消费**

- 消费者组中的消费者分摊消费 topic 中的消息。即 RocketMQ 会将 topic 中的队列均匀的分给组内各个消费者，一个队列只会被一个消费者消费，实现负载均衡，同时保证消费不被重复消费。

2. **广播消费**

- 消费者组内的所有消费者都要消费 topic 中的所有消息。
- 可以用广播模式将信息同步到所有节点，实现生产者发布一条消息，所有消费者都能消费。

# 四、事务消息

- RocketMQ 事务消息通过 **TransactionListener** 接口实现事务消息。

1. 生产者首先发送一条**半消息**，如果发送成功，则存储在 Broker 中并标记为 **prepared** 状态。
2. 生产者**执行本地事务**，如果执行成功，通知 Broker 将半消息还原为原始消息并发送给消费者。如果执行失败，通知 Broker 回滚消息，修改消息状态为 rollback 并从日志中删除该消息。
3. 如果 Broker 长时间没有收到生产者的 commit 或 rollback 消息，会发送一条**检查请求**，通过**回调**方法检查事务执行结果。

# 五、消息顺序性

- 保证同一流程的消息发送到同一个队列中，只能由同一个消费者消费该队列的消息。
- 可以通过自定义 `MessageQueueSelector` 实现按业务中唯一 id 进行路由，可以保证同一个流程的消息被发送到同一个队列。

# 六、延迟消息

## (一) RocketMQ 4.x

- RocketMQ 有 18 个延迟级别，对应了 18 个延迟队列。
- 生产者发送延时消息后，Broker 会将消息的原 Topic 和队列 id 作为属性保存在消息中，然后将消息 topic 改为内置的`**SCHEDULE_TOPIC_XXXX**`，并用延迟级别计算**延迟队列 id**。
- 改造后的消息写入 **CommitLog**，且将消息索引放进延迟队列。消费队列中该消息的索引单元中存储 tag 的字段用来存储消息的应该投递的时间戳。
- Broker 通过延迟消息服务 `ScheduleMessageService` 为**每一个延迟级别创建一个独立定时任务**，定时器会持续扫描对应的延迟队列，如果消息的投递时间 <= 系统时间，则将其取出。
- 然后恢复 Topic 并重新写入 CommitLog，转发到原始队列，接下来就作为普通消息被消费者消费。

## (二) RocketMQ 5.x

- **时间轮**是一个环形数组，每一个元素代表一个时间单位，元素记录该时刻到期的第一条消息在 TimerLog 中的位置。
- **TimerLog** 是顺序追加的日志，记录延迟消息的元数据（消息在 CommitLog 中的物理位置、投递时间等），通过指针将同一时刻到期的消息链接成链表。

# 七、死信队列

- 死信队列用于处理无法被正常消费的消息，即死信消息。
- 消息消费失败，RocketMQ 会自动进行消息重试。达到最大重试次数后，若消费依然失败，则表明消费者在正常情况下无法正确地消费该消息。此时，RocketMQ 不会立刻将消息丢弃，而是将转发到死信队列。
- 死信消息的特点

- 不会再被消费者正常消费。
- 有效期与正常消息相同，均为3天，3天后会被自动删除。因此，需要在死信消息产生后的3天内及时处理。

- 死信队列的特点

- 一个死信队列对应一个消费者组 **GroupID**，而不是对应单个消费者实例。
- 如果一个 GroupID 未产生死信消息，RocketMQ 不会为其创建相应的死信队列。
- 一个死信队列包含了对应 GroupID 产生的所有死信消息，不论该消息属于哪个 Topic。

# 八、怎么保证消息不丢失/可用性/可靠性

## (一) 生产阶段

- 主要通过**请求确认**机制，保证消息可靠传递。
- 同步发送时要等到 Broker **响应**才继续，通过响应或异常确认消息是否发送成功。
- 异步发送带有**回调**函数，可以在回调函数中检查是否发送成功。

## (二) 存储阶段

- Broker 消息**持久化刷盘**分为同步和异步。同步刷盘等消息完全持久化到磁盘后才返回响应；异步刷盘只能保证消息刷到 pagecache 就可以返回响应。
- Broker 可以配置**集群**，通过主从模式保证高可用，且支持主从同步、异步复制。

## (三) 消费阶段

- 消费者应该保证**消费完成再发送确认**而不是收到消息后立即确认。

# 九、这么保证消息消费的幂等性

## (一) 业务幂等

- 在消费者中保证同一条消息只消费一次。

## (二) 消费幂等

- 业务中，对同一条消息只消费一次，重复消息不再消费。
- 可以建立消费记录表，并设置唯一索引，拿到消息执行插入操作.

# 十、消息积压怎么处理

## (一) 控制消息积压问题

### 1. 消费者扩容

- 但是一个队列同一时刻只能被一个消费者机器占有，所以当消费者数量达到队列数量时，增加消费者数量也没用。

### 2. 消息降级

- 业务关键消息优先消费，非核心消息降级消费。

### 3. 启用临时 Topic

- 用单独的消费者拉取原 Topic 的消息然后原封不动地转发到临时 Topic 中，然后再消费该 Topic 或流量低的时候再转发回去。

## (二) 定位问题

- 消息计算太慢。
- 查数据库，可能存在慢查询、锁竞争。
- 调用三方接口，三方接口响应慢或网络 IO 慢。
- 消费逻辑有问题，消息经常失败。

## (三) 如果是热 Key 导致的消息积压

- 消息路由算法会将同一个 Key 的消息路由到同一个消费队列，导致该队列成为瓶颈。

### 1. 热 Key 拆分

- **逻辑拆分**：在热 Key 后面追加后缀，让这个 Key 的消息路由到不同的队列中。
- **修改路由算法**：如果这个 Key 的消息没有顺序消费的要求，可以通过轮询或其他路由算法，避免路由到同一个队列。

### 2. 生产者消息聚合

- 生产者发送消息之前，将一定窗口内的消息合并成一条消息，减少消息总量。
